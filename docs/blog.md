> 作者：周山翔（福州大学 · 数据科学与大数据技术）

## 一、写在前面

《羊了个羊》《抓大鹅》这类休闲小游戏，规则一句话就能讲完，做起来却不简单：
界面要能看、交互要顺手、状态要管清楚、算法还不能错。

「一箭又一箭」的核心规则非常干净：

> 点击一个箭头，如果它前进方向上没有别的箭头挡路，它就飞出棋盘被消除；
> 被挡住则不能消除，并且扣一次失误。清空全部箭头过关，失误用光失败。

规则简单到几乎不需要设计文档，但真正动手才发现有几个地方必须想清楚：

1. **路径检测怎么算**：箭头只能沿自己朝向的那一行或那一列走，向边界逐个格子推进，遇到第一个箭头就判定为被挡。
2. **一次点击要同时驱动逻辑和动画**：箭头要真的飞出去、被挡的箭头要给出「撞了一下」的反馈，而且不能因为动画还没播完就出现状态错乱。
3. **关卡必须真的能通关**：手摆的布局很容易摆出「几支箭头互相挡死」的死局。这是最容易翻车的地方，后面会详细讲。
4. **`pygame.font.SysFont()` 在部分 Windows 机器上会崩溃**：这是我这次踩到的真实坑。
5. **关卡一多，「难」就得先定义清楚**：AI 生成的关卡都能通关，却没有一关是难的——
   因为对这个玩法来说，唯一会输的方式是点错一支被挡住的箭头，所以「难」等于「一眼看不出哪些能点」。
   这件事我是在第四节「记录 5」里才想明白的。
6. **进度存档的异常路径不能被忽略**：存档损坏不能让游戏起不来（第四节「记录 6」）。

**最终成品包含**：12 个关卡（1 个逐步引导的教学关 + 11 个难度递增的常规关，棋盘从 4×5 到 10×10）、
关卡总览界面（一眼看清已通关 / 可挑战 / 未解锁）、逐关解锁与进度存档，
以及开始界面、游戏界面、通关与失败界面。

整个项目我用 AIGC 工具辅助完成，AI 承担了大部分代码编写，我负责需求拆解、审查代码、
提供运行反馈、定位问题和验收。下面把过程如实记录下来。

## 二、技术选型与整体设计

### 2.1 为什么选 Pygame

作业允许 Pygame / Pygame Zero / Tkinter 等。选 Pygame 的理由很直接：

* 动画和逐帧控制是它的主场，箭头飞出、抖动、飘字都好做；
* 用 Surface 缓存 + `transform.rotate` 可以把「画一次朝右的箭头，再旋转出四个方向」，
  不用为四个方向各画一套素材；
* 无头运行方便：把 `SDL_VIDEODRIVER` 设成 `dummy`，就能在不开窗口的情况下批量生成截图、跑测试。

### 2.2 模块划分：把逻辑和界面彻底拆开

我先让 AI 帮我拆了一遍模块，得到的是「一个几百行的 main.py 里什么都有」。
这个方案能跑，但没法测——规则逻辑和 `pygame.display` 搅在一起，写测试就得先开窗口。

所以我要求按下面这种方式重做，核心原则是 **`board.py` 不许 import pygame**：

```
game/
├── config.py   全局配置：窗口尺寸、配色、字体路径、动画参数
├── board.py    棋盘规则：路径检测 / 飞出 / 失误 / 胜负判定（纯 Python，无 pygame）
├── levels.py   关卡数据：ASCII 布局 + 解析 + 校验
├── ui.py       绘图工具：字体、文字、按钮、箭头图形
├── anim.py     动画：飞出、撞击抖动、飘字
└── app.py      游戏主体：场景状态机、事件分发、渲染
```

这个改动带来的收益非常明显：

* `board.py` 可以用纯逻辑测试覆盖，跑一次不到 0.1 秒；
* 关卡是否有解可以脱离游戏单独验证；
* 界面改版不会碰到规则代码。

### 2.3 状态机：只用一个 click 入口

所有对棋盘的修改都必须经过 `Board.click(row, col)`，它返回一个 `ClickResult`：

```python
def click(self, row, col):
    if self.state != STATE_PLAYING:
        return ClickResult(CLICK_IGNORED)      # 本关已经结束
    if not self.in_bounds(row, col):
        return ClickResult(CLICK_IGNORED)      # 点到棋盘外

    arrow = self.grid[row][col]
    if arrow is None:
        return ClickResult(CLICK_EMPTY)        # 点到空格，不扣失误

    blocker = self.find_blocker(row, col)
    if blocker is None:                        # 前方无阻挡 -> 飞出
        self.grid[row][col] = None
        self.remaining -= 1
        if self.remaining == 0:
            self.state = STATE_CLEARED
        return ClickResult(CLICK_FLY, arrow, None, path)

    self.mistakes += 1                         # 前方有阻挡 -> 扣失误
    if self.mistakes >= self.max_mistakes:
        self.state = STATE_FAILED
    return ClickResult(CLICK_BLOCKED, arrow, blocker, path)
```

界面层拿到返回值后只做一件事：决定播哪个动画。**逻辑和表现彻底分离**，
测试可以完全绕过渲染直接验证规则，动画也永远不会反过来改状态。

场景只有两个：`SCENE_MENU`（开始界面）和 `SCENE_PLAY`（游戏界面）；
通关 / 失败 / 全部通关是以半透明面板（overlay）叠加在游戏界面上的，
面板弹出后棋盘点击被拦掉，避免误触。这样不用为每种结果再写一遍棋盘渲染。

## 三、核心实现

### 3.1 路径检测

这是整个游戏的算法核心，两段代码就够了：

```python
def path_cells(self, row, col):
    """该箭头前进方向上、直到棋盘边界的全部格子坐标（不含自身）。"""
    arrow = self.grid[row][col]
    d_row, d_col = arrow.delta          # 方向 -> (行增量, 列增量)
    cells = []
    r, c = row + d_row, col + d_col
    while self.in_bounds(r, c):
        cells.append((r, c))
        r += d_row
        c += d_col
    return cells

def find_blocker(self, row, col):
    """返回前进方向上第一个挡路的箭头；路径通畅返回 None。"""
    for r, c in self.path_cells(row, col):
        if self.grid[r][c] is not None:
            return self.grid[r][c]
    return None
```

因为四个方向都被统一成 `(行增量, 列增量)`，所以**不需要写四份判断分支**：
朝上就是 `(-1, 0)`，朝右就是 `(0, 1)`，`while` 循环天然只沿一个方向推进，
边界由 `in_bounds()` 兜住，从根上避免了「向上判断时数组越界」这类经典错误。

### 3.2 飞出与撞击的表现

* **飞出**：`FlyOut` 动画用 `progress ** 1.7` 做缓入，看起来像被抽出去一样越来越快，
  飞出距离按「箭头位置 → 棋盘边界 + 0.9 个格子」计算，保证彻底离场；最后 28% 的时间里淡出。
* **撞击**：`Impact` 动画做三件事——沿方向前冲 18% 格宽再弹回（`sin` 曲线）、
  垂直于前进方向做衰减抖动、单元格泛红并向外扩散一圈红框，
  同时箭头颜色向红色插值；再配一条向上飘的「被挡住了 -1 失误」提示。
  整个动画 0.36 秒，结束后自动从动画列表移除。

### 3.3 一个顺手加的小功能：悬停显示路径

鼠标停在箭头上时，把它前进方向上的格子点亮：**绿色 = 畅通，红色 = 被挡**，
并用红色边框标出具体是哪一支箭头挡住了它。

这个功能是调试期的副产品——一开始只是为了确认路径检测算得对不对，
后来发现它对玩家很友好（能看懂「为什么这支箭飞不出去」），就留下了。

它一开始有个小毛病：红色高亮会把挡路箭头**之后**的格子也点亮，
视觉上让人以为「后面的都算被挡」，改成截断到挡路箭头为止就对了。

### 记录 1：第 2 关摆出了死局

**我的要求**：设计 4 个难度递进的关卡，用 ASCII 布局表示，第 2 关要「有且只有一支箭能直接飞出去」，
用来教玩家「先找出口」。

**AI 提供**：直接给了 4 关布局。第 2 关长这样：

```
.....          (1,1) 的「>」被 (1,3) 的「v」挡住
.>.v.          (1,3) 的「v」被 (3,3) 的「<」挡住
.....          (3,3) 的「<」被 (3,1) 的「^」挡住
.^.<.          (3,1) 的「^」被 (1,1) 的「>」挡住
.....
```

**实际效果**：开局可点的箭头数量是 **0**。四支箭头首尾相接围成一个环，
互相指责，谁都飞不出去——这一关是**无解**的。

**我的处理**：其实我当时也没一眼看出来，是写完校验脚本后报的警：

```
第2关 交叉路口  5×5  箭头4  初始可点0  可解=False
```

顺着「谁挡住了谁」捋一遍就明白了。修改办法很简单：把 `(3,3)` 的 `<` 挪到 `(3,4)`，
它左边依然是 `(3,1)` 的 `^`（保持阻挡关系不变），但不再挡在 `(1,3)` 的 `v` 下方了：

```
.....
.>.v.
.....
.^..<
.....
```

再校验：

```
第2关 交叉路口  5×5  箭头4  初始可点1  可解=True
       参考顺序：(1,3)下 -> (1,1)右 -> (3,1)上 -> (3,4)左
```

刚好是我想要的「唯一的出口 + 四步连锁」效果。

**这件事的价值**：它让我意识到**关卡不能靠眼睛验收**。
后来我把「所有关卡必须可解」直接写成了单元测试，布局一改就会被自动拦住。

### 记录 2：为什么用贪心判断关卡有解

**我的要求**：写一个脚本，能自动判断关卡能不能通关，并且给出一个参考通关顺序。

**AI 提供**：反复扫描棋盘，把当前能飞出的箭头全部消掉，直到不能再消；
如果还有剩余箭头就说明无解。

**实际效果**：跑起来完全正确。但我不太放心——「每次都消所有能消的」这种贪心，
会不会因为选择顺序不合适而漏掉真正的解？

**我的处理**：我补了一个证明，并把它写进了代码注释里：

> 消除一个箭头只会让其它箭头的路径**变得更空**，永远不会让某条路径变得更堵。
> 也就是说「某箭头此刻能飞出」这个性质具有**单调性**：此刻能飞，之后任何时刻都还能飞。
> 既然不会因为选择而失去任何机会，那么反复「消掉当前所有能飞的」就是完备的——
> 能全消掉就一定有通关顺序，卡住了就说明真的无解。

另外我还专门构造了一个**必然死锁**的布局做反向验证：

```python
layout = ("....", ".><.", "....", "....")   # 同一行两个箭头面对面
self.assertIsNone(solve_level(level.rows, level.cols, level.arrows))
```

这个用例跑通之后，我才确信校验脚本是可信的。

### 记录 3：`pygame.font.SysFont()` 在本机直接崩溃

**我的要求**：界面全中文，需要加载系统中文字体。

**AI 提供**：教科书式的写法：

```python
font = pygame.font.SysFont("Microsoft YaHei", 32)
```

**实际效果**：在这台 Windows 机器上，这一行**直接抛异常**：

```
File "pygame\sysfont.py", line 82, in initsysfonts_win32
    if splitext(font)[1].lower() not in OpenType_extensions:
TypeError: expected str, bytes or os.PathLike object, not int
```

原因是 pygame 枚举注册表里的字体项时，碰到了不是字符串的条目，属于 pygame 2.6.1
在特定 Windows 字体环境下的兼容问题——**这是只有真的跑起来才会暴露的错误**。

**我的处理**：不再依赖 `SysFont` / `match_font`，改成自己按路径找字体文件：

```python
FONT_PATHS = [
    r"C:\Windows\Fonts\msyh.ttc",       # 微软雅黑
    r"C:\Windows\Fonts\simhei.ttf",     # 黑体
    r"C:\Windows\Fonts\Deng.ttf",       # 等线
    "/System/Library/Fonts/PingFang.ttc",
    "/usr/share/fonts/opentype/noto/NotoSansCJK-Regular.ttc",
]

def font_file(bold=False):
    for path in (config.FONT_BOLD_PATHS if bold else config.FONT_PATHS):
        if os.path.exists(path):
            return path
    return None       # 都没找到 -> 退化为 pygame 默认字体，同时在控制台警告
```

这样跨平台都能用，找不到字体也不会崩，只是中文会显示成方块并给出提示。

### 记录 4：测试用例首轮 4 个失败

**我的要求**：按作业给的 T01–T06 写自动化测试。

**AI 提供**：23 个用例，逻辑看着都对。

**实际效果**：第一次运行 **4 个失败**，原因分成两类，都不是源码的问题，而是测试自己写错了：

第一类，**测试关卡的箭头数写错了**。

```
AssertionError: 2 != 3        # test_t01_click_free_arrow_flies_out
AssertionError: 3 != 4        # test_t02_click_blocked_arrow_costs_a_mistake
```

我先定义了测试用小关卡：

```python
BASIC_LAYOUT = ("....", ".>v.", "....", ".^..")
```

这支布局其实只有 **3 支**箭头（(1,1) 右、(1,2) 下、(3,1) 上），
但断言里按 4 支写。是 AI 把先前另一个草图的数量记串了。

第二类，**测试辅助函数把「已经飞出去的箭头」当成了「被挡住的箭头」**：

```python
def blocked_arrow(self, board):
    for arrow in board.arrows:
        if not board.can_fly(arrow.row, arrow.col):
            return arrow        # BUG：箭头飞出去后 can_fly 也是 False
```

`board.arrows` 保存的是**关卡初始的全部箭头**（用于重开时复位），
箭头飞出去之后它依然在列表里，但已经不在 `grid` 上了，于是 `can_fly` 返回 False，
辅助函数就会误把它当成"被挡住的箭头"，结果点击时命中空格、根本不扣失误，测试自然失败。

**我的处理**：断言数值按实际布局改成 3 / 2 的对应关系；
辅助函数加一句「必须还在棋盘上」的过滤：

```python
def blocked_arrow(self, board):
    for arrow in board.arrows:
        if board.arrow_at(arrow.row, arrow.col) is not arrow:
            continue            # 已经飞出去了，跳过
        if not board.can_fly(arrow.row, arrow.col):
            return arrow
```

修完再跑，23 个用例全绿：

```
Ran 23 tests in 0.334s
OK
```

> 顺带一提：这是**首版**测试的数量。后面把关卡扩到 12 关、又加了关卡总览、
> 逐关解锁和教学关之后，用例扩到了 **48 个**，最终结果见第六节。

**这件事的价值**：测试失败不等于源码有 bug，也可能是测试自己在说谎。
两次都不是改游戏，而是改测试——但**前提是你得先看懂源码到底怎么运行的**，
这也正好说明「AI 生成的代码必须自己理解」不是一句空话。

### 记录 5：让 AI 生成关卡，结果它挑出来的全是最简单的

**我的要求**：在原有 4 关之外再加 8 关，难度要递增，而且每一关都必须能通关。
随机撒箭头很容易撒出无解布局，所以我要求 AI 写一个生成器，用已有的求解器当验收。

**AI 提供**：`tools/generate_levels.py`，思路是「随机撒箭头 → 用贪心求解器筛掉无解的 → 按难度分排序取前几名」。

**实际效果**：筛出来的关卡确实都能通关，但**全部是开局几乎每支箭头都能飞出去的松布局**。
10×10 摆 30 支箭头，开局可点 24 支——玩家随便点都能过，难度根本谈不上。
翻代码才发现，排序那行我把方向写反了：难度分里「开局可飞行数」是负权重，
我却按升序取前几名，等于专门挑最简单的。改成降序之后好了一些，但开局可点数还是有十几支。

**我的处理**：先停下来想清楚一件事——**这个游戏到底难在哪里**。

规则里有个容易被忽略的性质：点击一支能飞出去的箭头，只会让别的箭头路径更空，
所以**任何一步「正确操作」都不会把自己玩死**。也就是说，这个游戏没有「顺序错误」这个概念，
唯一会输的方式是**点了一支其实被挡住的箭头**。

那么难度就只能来自一件事：**在棋盘上找出此刻哪些箭头的前方是空的**。
棋盘越大、开局能点的越少，需要扫视的线条就越多，难度越高。

想通这点之后，生成器换成了两条新做法：

* **逆向构造**：把「消除顺序」倒过来当「放置顺序」，放置时只要求「新箭头正前方没有已放置的箭头」，
  这样放置顺序的逆序天然就是一个合法通关顺序，布局**必然可解**，连事后筛选都不需要；
* **阻挡偏好**：维护一张 `seen` 表，记录每个格子「被多少支已放置箭头的射线覆盖」，
  放置新箭头时优先选这些格子——新箭头正好落在老箭头前方，老箭头就得等它先走。
  这张表让判断「这格会不会挡住别人」变成 O(1)，不然每放一支都要重扫全盘。

结果：同样是 10×10 / 30 支箭头，开局可点数从 24 支压到 **7 支**，
全程平均可选数从 12 降到 4.2，玩起来才真的需要一行一行地扫。

**这件事的价值**：排序方向写反是个很低级的错误，但更值得注意的是——
**AI 不会觉得「挑出来的关太简单」有什么不对**，因为它没有「这一关玩起来应该是什么感觉」的直觉。
「什么叫做难」这件事必须由人先定义清楚，再翻译成能写进代码的指标。

### 记录 6：进度用 pickle 存，看着能用其实是个雷

**我的要求**：记录玩家已经通关到第几关，没通关前面就不让玩后面；关掉游戏再打开，进度还在。

**AI 提供**：把已通关关卡的下标集合 `pickle` 到一个文件里，启动时 `pickle.load` 读回来。

**实际效果**：能跑。但有两个问题一看就心里发毛：

1. `pickle` 是二进制，存档出问题时**打不开也看不懂**；
2. 只要文件损坏（比如写到一半断电），`pickle.load` 会直接抛异常，
   **整个游戏在启动时就崩掉**——对一个要交给老师演示的作业来说这是致命的。

**我的处理**：

* 换成 JSON：存档打开就是 `{"version": 1, "cleared": [0, 1, 2]}`，一眼能看懂；
* 加容错：读失败当作空进度，写失败只在控制台警告一次，游戏照常能玩。
  这是一个有取舍的决定——严格报错更「正确」，但演示场景下「能继续玩」更重要；
* 把解锁规则从界面代码里抽出来，放到不依赖 pygame 的 `progress.py`，
  于是「通关一关才解锁下一关」这条规则可以用普通单测覆盖（8 个用例），
  不必为了测一条 `if` 去创建窗口。

**这件事的价值**：AI 给出的方案经常是「功能可用」就停了，**异常路径完全是空白**。
凡是会落盘的东西，都要自己问一句：文件损坏了会怎么样？目录没写权限会怎么样？

### 记录 7：加完新功能，回归挂了两个用例

**背景**：把 4 关扩到 12 关，并加上关卡总览、逐关解锁、教学关之后，跑一遍回归，
48 个用例挂了 2 个。两个都挺有意思。

**坑 A：`test_t06_restart_mid_game` 报「本关没有找到被挡住的箭头」**

测试本身没写错，是**关卡数据变了**：教学关被插到了第 1 关，而它只有 3 支箭头，
消掉一支之后剩下两支都畅通，再也制造不出「点击被挡住的箭头」这个场景。

改法是把 T06 挪到第 2 关（初次拉弓）——它同时存在能飞的和被挡的箭头。
顺带意识到一个更根本的问题：**测试里写「第 1 关」就是一种隐式耦合**，
一旦关卡表调整就会连带失效。所以改成显式指定关卡下标，并把「这一关要有被挡的箭头」
写成辅助函数里的断言，下次再挂就能一眼看出是数据问题还是逻辑问题。

**坑 B：`test_reset_progress_needs_two_clicks` 报「点了两次还在确认态」**

看代码就明白：「清空进度」按钮的确认分支里**忘了把 `reset_armed` 复位**，
于是按钮文字永远停在「确认清空？」。这种漏写人眼一扫很容易放过，测试一秒钟就抓到了。

**还有两个只有看图才能发现的问题**

跑完测试全绿之后我照例重新生成截图，一张一张看，发现两处：

* **「先通关第 N 关吧」的提示气泡会跟着玩家进入关卡**——因为切换场景时没有清掉气泡计时器，
  点了一张锁着的卡片再进教学关，气泡还赖在屏幕上；
* **教学关的高亮环把箭头压暗了**——高亮环的呼吸填充画在箭头之后，
  半透明的琥珀色盖在箭头上，看着像蒙了一层灰。改成底色画在箭头下方、只有外环画在最上层。

这两个都不是逻辑错误，**测试也测不出来**——是靠生成截图后逐张检查发现的。

**这件事的价值**：自动化测试能守住「逻辑对不对」，守不住「看起来对不对」。
一个可运行 + 可测试 + **有截图可复查**的项目，验收时才算闭环。

**难度是怎么控制的**

这个游戏有个容易被忽略的性质：点掉一支能飞出去的箭头，只会让其它箭头的路径更空，
所以**任何一步正确操作都不会把自己玩死**——它不存在「顺序错误」，
唯一会输的方式是点了一支其实被挡住的箭头。因此难度**只来自一件事：
在棋盘上找出此刻哪些箭头的前方是空的**。

于是两个指标决定了难度：

* **开局可直接点掉的箭头数量**——越少越要在开局就仔细扫视；
* **棋盘大小**——格子越多，需要顺着看的行与列就越多。

失误上限则是「惩罚力度」：早期关卡给 4~5 次，允许边试边学；
最后几关只给 2 次，点错两次就重来。

难度分按 `箭头数 × 1.6 + 棋盘格数 ÷ 6 − 开局可点数 × 2.0 − 失误上限 × 1.5` 计算，
再映射成 1~5 颗星显示在关卡总览里。前 5 关是手写的（教学 + 熟悉规则），
第 6 关之后的 7 关由 `tools/generate_levels.py` **逆向构造**生成，
思路见第四节「记录 5」。

`python tools/verify_levels.py` 的输出（每关都会同时打印布局和参考通关顺序，这里只节选汇总）：

## 五点五、把关卡串起来的三件事

关卡变多之后，只靠「开始游戏」一路打下去已经不够用了，所以另外做了三件事。

### 5.5.1 教学关：把规则讲一遍，不如让玩家点一遍

教学关不只是一张简单的棋盘，它会**逐步引导**：当前该点的箭头套一圈会呼吸的黄色高亮环，
底部有一条讲解条写着「为什么点这一支」，右上角显示「教学 2 / 4」的进度。

四步的设计是刻意安排的：

| 步骤 | 引导玩家做什么 | 想让他学到什么 |
| --- | --- | --- |
| 1 | 点一支**前方有阻挡**的箭头 | 碰撞反馈长什么样、失误是怎么扣的 |
| 2 | 点那支挡住它的箭头（它前方是空的） | 什么叫「前方没有阻挡就能飞出去」 |
| 3 | 再回去点第 1 步那支箭头 | 挡路的走了，原本飞不出去的就通了 |
| 4 | 点掉最后一支 | 清空即通关 |

这里有个必须处理的现实问题：**玩家完全可以不按提示点**。
所以引导在每一步展示前都会和棋盘状态对一次账——目标格子已经飞走了、或者这一步的前提
（比如「它被挡住了」）已经不成立了，就**自动跳到下一步**，绝不会出现
「让你去点一支已经不在棋盘上的箭头」这种尴尬。

这一步的实现在 `Game.sync_tutorial()`，也是我这次比较满意的一小段代码。

### 5.5.2 关卡总览：一眼看清 12 关的进度

主菜单里加了「关卡总览」入口，12 张卡片按 4×3 排开，每张显示关卡序号、名称、
棋盘规格与箭头数、难度星级，以及三种状态之一：

| 状态 | 视觉 | 能不能点 |
| --- | --- | --- |
| 已通关 | 绿色底 + 对勾 + 绿色边框 | 能，随时重玩 |
| 可挑战 | 深蓝底 + 难度星级 | 能，点击直接开局 |
| 未解锁 | 暗底 + 挂锁图标 | 不能，点击会提示「先通关第 N 关」 |

### 5.5.3 逐关解锁与进度存档

**没过完前面的关卡，就不让玩后面的**——这条规则由 `game/progress.py` 负责，它不依赖 pygame，
所以能用普通的单元测试覆盖（`ProgressTestCase`，8 个用例）。

规则本身很简单：从第 1 关往后数，遇到第一个没通关的关卡就停下——它自己是解锁的，再往后都锁着。
注意这里**跳着通关不算数**：如果通过某种方式标记了「第 3 关已通关」但第 2 关没过，
解锁进度依然停在第 2 关。这条我专门写了用例覆盖。

进度存在项目根目录的 `progress.json`：

```json
{
  "version": 1,
  "cleared": [0, 1, 2]
}
```

存档用的是 JSON 而不是 `pickle`，原因写在第四节「记录 6」里。另外有两条容错：

* **读失败**（文件不存在、内容损坏）当作空进度，游戏照常启动；
* **写失败**（目录只读之类）只在控制台警告一次，不影响继续玩。

关卡总览里还有一个「清空进度」按钮，需要**点两次**才真的清——第一次点会变成「确认清空？」，
点别的地方就取消，避免手滑把存档删了。

| 教学关引导推进 | 按提示逐步点击，4 步依次推进，最后引导结束 | ✅ |
| 教学关引导自愈 | 玩家不按提示点时，失效的步骤被自动跳过，不会卡在错误的一步 | ✅ |
| 12 关顺序通关 | 从第 1 关一路打到第 12 关，验证解锁链路与全部关卡数据 | ✅ |

### 6.4 手动试玩验证

自动化测试只能证明「逻辑上可解」，不能证明「玩起来是对的」。
下面每一关我都按参考顺序实机点了一遍，确认手感、动画和反馈正常：

| 关卡 | 试玩结论 |
| --- | --- |
| 第 1 关 教学关 | 黄色高亮环一眼就能看到该点哪支；故意点被挡的箭头会立刻看到红色撞击和「-1 失误」 |
| 第 2 关 初次拉弓 | 5 支箭头，随便点也能过，适合熟悉规则；动画节奏舒服 |
| 第 3 关 交叉路口 | 开局只有 (1,3) 的「v」能飞；点错立刻看到红色撞击反馈，教学效果好 |
| 第 4 关 连锁反应 | 先点 (1,5) 的「v」，一行四个「>」会依次飞出，连锁感很明显 |
| 第 5 关 四面楚歌 | 只有 (1,5) 能先飞；3 次失误的容错不算大，点错两次就得想清楚再动手 |
| 第 6~8 关 | 棋盘开始变大（7×8 / 8×8 / 8×9），开局可点的箭头有 3~5 支，横竖都要扫一遍 |
| 第 9~12 关 | 9×9 到 10×10，30 支箭头摆满整张棋盘；只有 2 次失误，基本要「想清楚了再点」 |
| 通用 | 「重新开始」后布局和失误次数都正确复位；`Esc` 返回主菜单、`R` 重开都正常；通一关后总览里那一张卡片立刻变绿并解锁下一张 |

> 这一节的结论需要在**本人实际试玩后确认**，如果手感和这里写的不一致，以真实感受为准改掉。

## 七、遇到的问题汇总

| 问题 | 现象 | 原因 | 解决方式 |
| --- | --- | --- | --- |
| 第 2 关无解 | 校验脚本报 `可解=False`，开局可点箭头为 0 | 4 支箭头首尾相接形成死环 | 把 `<` 从 (3,3) 移到 (3,4)，重新校验 |
| 中文字体加载崩溃 | `TypeError: ... not int` | pygame 枚举 Windows 注册表字体时崩溃 | 改为按路径直接加载 `msyh.ttc` 等字体文件 |
| 测试首轮 4 个失败 | 断言数值对不上 / 点击不扣失误 | 测试关卡的箭头数写错；辅助函数把已飞出的箭头当成被挡的 | 按实际布局修正数值；辅助函数加「箭头仍在棋盘上」的过滤 |
| 悬停高亮高亮了不该高亮的格子 | 挡路箭头之后的路段也被点亮 | 高亮用了完整路径，没在阻挡处截断 | 把路径截断到挡路箭头为止 |
| 动画还没播完就弹出结果面板 | 最后一支箭头还在飞，通关面板已经盖上来 | 状态切换和动画没有解耦 | 通关 / 失败后延迟 0.70 秒再弹面板，动画时长 0.45 秒 |
| 生成的关卡全是简单关 | 10×10 摆 30 支箭头，开局可点 24 支 | 难度分排序方向写反，等于专挑最简单的 | 改成降序，并换成「逆向构造 + 阻挡偏好」，开局可点压到 7 支 |
| 加关卡后 T06 用例失败 | 报「本关没有找到被挡住的箭头」 | 教学关插到了第 1 关，它只有 3 支箭头，消一支后全部畅通 | 把 T06 挪到第 2 关，改成显式指定关卡下标 |
| 「清空进度」点了两次还在确认态 | 按钮文字停在「确认清空？」 | 确认分支里忘了把 `reset_armed` 复位 | 清空后先复位再重建按钮 |
| 提示气泡跟着进了关卡 | 点锁着的卡片后进教学关，气泡还在屏幕上 | 切换场景时没有清掉气泡计时器 | 把气泡清理并入场景公共清理函数 |
| 教学高亮把箭头压暗 | 目标箭头看着像蒙了一层灰 | 高亮环的半透明填充画在箭头之后 | 底色改画在箭头下方，只有外环画在最上层 |
| 存档用 `pickle` 有崩启动的风险 | 文件损坏时 `pickle.load` 直接抛异常 | 方案没有考虑异常路径 | 换 JSON + 读写容错（读失败当空进度，写失败只警告） |

## 八、心得体会

1. **AI 写代码很快，但「验收」只能靠自己。** 这次真正花时间的不是写代码，
   而是把每个环节真的跑一遍：一跑就发现字体崩溃、一跑就发现第 2 关无解。
   代码看起来再对，不运行就不算数。
2. **能自动校验的东西一定要自动校验。** 「关卡必须可解」这件事，用眼睛看 4 个布局也许能看出来，
   但关卡一旦扩到 12 个就必然出错。写成求解器 + 单元测试之后，改布局完全不慌。
3. **让 AI 给出「可测试的结构」，比让它一次写对更重要。** 把 `board.py` 和 pygame 彻底隔开之后，
   规则测试从「要开窗口、要模拟鼠标」变成「三行代码断言一个状态」，效率差了一个数量级。
   后来加进度解锁也是同一招——抽出 `progress.py`，一条 `if` 也能被单测覆盖。
4. **测试失败不一定是源码的问题。** 这次 4 个失败全是我自己（或 AI）写的测试有问题，
   但排查过程必须回到源码去看 `grid` 和 `arrows` 的区别——这也是为什么「必须理解自己提交的代码」。
5. **「难」这件事得由人来定义。** 让 AI 生成关卡时，它给出的关卡逻辑上都成立、都能通关，
   但没有一关是「难」的——因为它没有玩过游戏，不知道什么叫难。
   我先想清楚「这个游戏唯一会输的方式是点错一支被挡住的箭头」，
   才能把「难」翻译成「开局可飞行数要少、棋盘要大」这两个能写进代码的指标。
6. **测试全绿不等于做完了。** 加完关卡那次，48 个用例全过，但截图一看就发现
   提示气泡跟着进了关卡、教学高亮把箭头压暗了。逻辑正确和看起来正确是两件事，
   所以我把「自动生成截图」也做成了项目的一部分，方便每次改完都过一眼。

## 九、如何运行

```bash
git clone https://github.com/zsx123456/one-arrow-after-another.git
cd one-arrow-after-another
pip install -r requirements.txt
python main.py
```

第一次运行会直接落在开始界面，点「开始游戏」会带你走一遍教学关。
此后每次启动都会读取项目根目录的 `progress.json`，接着上次的进度继续
（这个文件已经加进 `.gitignore`，属于本机状态，不会上传）。
想从头再来就在「关卡总览」里点两次「清空进度」。

详细的环境说明、操作方式和常见问题见仓库的 `README.md`。
