## 二、项目介绍

### 2.1 游戏规则

棋盘上散布着许多**管道**。一支管道是一条占若干格的**折线**，末端长着一个箭头，
朝向「上 / 下 / 左 / 右」四个方向之一。玩家点击某支管道的**任意一格**：

* 它**箭头**正前方那条射线上**没有别的管道**：整条管道沿自己的方向飞出棋盘并被消除；
* 射线上**有别的管道**：它不会消失，前冲一下再弹回、抖动、泛红，**丢掉一颗心**；
* 清空本关全部管道即通关，剩下的心越多，本关得分越高；
* 心用光则本关失败，可以重新开始。

### 2.2 界面设计

一共五个画面：**开始界面**、**关卡总览**、**游戏界面**、**结果面板**（通关 / 失败 / 全部通关 /
教学结束，都是叠在游戏界面上的半透明面板）、**设置面板**；
教学引导是游戏界面的一种模式。

游戏界面自上而下分成**三块**：**顶部信息栏 / 棋盘 / 底部工具栏**。

* 信息栏上一行是齿轮（设置）、昼夜开关、关卡标题与右侧胶囊「关卡总览」；
  下一行把**计时、生命值、剩余管道、本关得分**四组信息横排并**整体居中**。
  心数会随关卡变化（4~7 颗）、得分位数也会变，早期用一串写死的 x 坐标，
  每加一点内容都要人工核算会不会压住；现在先量出真实字宽再居中，内容怎么变都不会撞上。
* 棋盘**不画每一格的底框**，只有一片极淡的点阵。这个玩法的难度来自「在一堆管道里
  找出能点的那支」，几十个空方框会让视线一直被拽住——那是「乱」不是「难」。
* 底部工具栏：左边圆钮「提示」、中间缩放滑杆与百分比、右边圆钮「辅助线」，
  圆钮下面各标一行名字，开关打开时圆钮和字一起变蓝。

配色上，管道是一条**圆角粗管道**，末端一个三角箭头，颜色取自一组 12 色糖果色；
但**相邻（上下左右）的两支管道不允许同色**——同色管道挨在一起会连成一片、数不清有几支，
所以 `pieces.assign_colors` 用贪心染色避开了这件事。

两套主题（顶栏那个月亮 / 太阳开关切换）：`night`（深色，默认）和 `day`（浅色）。
两套配色的键名完全一样，切主题就是把另一份值写到同一批常量上，
界面代码一行都不用改。

## 三、实现思路

### 3.1 技术选型与模块划分

选 Pygame 的理由很直接：动画和逐帧控制是它的主场；用 Surface 缓存可以把
「一条管道的形状」画一次就反复复用；而且它**无头运行方便**——
把 `SDL_VIDEODRIVER` 设成 `dummy` 就能不开窗口批量出截图、跑测试。

我先让 AI 帮我拆了一遍模块，得到的是「一个几百行的 main.py 里什么都有」。
这个方案能跑，但没法测——规则逻辑和 `pygame.display` 搅在一起，写测试就得先开窗口。
所以我要求按下面这种方式重做，核心原则是**规则模块不许 import pygame**：

```
game/
├── config.py    全局配置：窗口尺寸、布局常量、两套主题配色、字体路径、动画参数
├── pieces.py    棋子模型：折线管道、方向、射线、布局校验、相邻不同色
├── board.py     棋盘规则：点击 / 路径检测 / 飞出 / 生命值 / 胜负判定（纯 Python）
├── levels.py    关卡数据：管道写法 + 教学步骤 + 难度评级 + 生命值表 + 校验
├── scoring.py   得分规则（纯函数）
├── progress.py  解锁规则与存档（纯 Python）
├── ui.py        绘图工具：字体、文字折行、按钮、滑杆、图标、像素心
├── anim.py      动画：整条管道飞出、撞击抖动、飘字、心碎
├── bgfx.py      动态背景
└── app.py       游戏主体：场景状态机、事件分发、渲染
```

收益非常明显：`board.py` / `pieces.py` / `progress.py` / `scoring.py` 都可以用纯逻辑测试覆盖，
跑一次不到 0.1 秒；关卡是否有解能脱离游戏单独验证；界面改版不会碰到规则代码。

> 顺带一提，`pieces.py` 是**这一版才拆出来**的。上一版棋子是「一格一支箭头」，
> 方向、颜色、坐标都能塞进 `board.py`；改成占多格的弯曲管道之后，
> 「解析写法 / 校验布局 / 算射线 / 分配颜色」这些几何活儿有 240 多行，
> 再和棋盘规则混在一起就没人看得懂了，于是单独成模块。

### 3.2 管道、方向和关卡怎么表示

**方向**用两个东西表示：一个字符 + 一个增量对。字符用于读写关卡，增量对用于算法。

```python
DIRECTIONS = {"up": (-1, 0), "down": (1, 0), "left": (0, -1), "right": (0, 1)}
DIR_CHARS = {"^": "up", "v": "down", "<": "left", ">": "right"}
SEG_CHARS = {"U": "up", "D": "down", "L": "left", "R": "right"}
```

把四个方向统一成 `(行增量, 列增量)` 是这一版最关键的设计决定，理由在 3.3 说。

**一支管道**就是一行字符串：`行,列 方向 路径`。

```
"4,6 > D3R2"     从第 4 行第 6 列出发，箭头朝右，
                 管道先向下 3 格、再向右 2 格，共 6 格
```

**箭头在路径的末端**——也就是最后经过的那一格。路径必须逐格相邻、不能和自己交叉，
而且**最后一段必须和箭头方向一致**（不然画出来的箭头会歪在拐角上）。

```python
Level(
    name="交叉路口",
    hint="开局能点的很少，先找朝外的",
    max_hp=4,
    rows=13, cols=9,
    specs=(
        "2,0 > R2",
        "0,8 ^",
        # ...
    ),
)
```

写法由 `pieces.parse_piece` 解析，宽进严出：路径段可省略（`"5,0 <"` 就是只占一格朝左的短箭）、
可小写、多余空格会被折叠。**这里踩过一个坑**：不能对整串调用 `upper()`——
方向字符里的 `v`（向下）大写之后会变成 `V`，而方向表里认的是小写 `v`，
于是所有朝下的管道都会解析失败。所以只把「路径段」那一段提出来大写，方向字符单独按小写查表。
测试里专门有一条 `test_parse_downward_piece_is_not_broken_by_upper` 钉住这件事。

`pieces.validate_layout` 在关卡导入时就做校验：都在盘内、互不重叠、逐格相邻、不自交、
末端一段与箭头方向一致、**射线不能穿过自己的身体**（否则这支箭永远飞不出去）。
**非法数据在构造时就报错**，不会等到画到屏幕上才发现。

### 3.3 路径检测（核心算法）

这是整个游戏的算法核心，两段代码就够了：

```python
def ray(self, rows, cols):
    """从箭头出发、沿箭头方向直到棋盘边界的格子（不含箭头自己）。"""
    d_row, d_col = self.delta
    row, col = self.head[0] + d_row, self.head[1] + d_col
    cells = []
    while 0 <= row < rows and 0 <= col < cols:
        cells.append((row, col))
        row += d_row
        col += d_col
    return cells

def path_to_blocker(self, piece):
    """返回 (射线上到挡路那支为止的格子, 挡路的管道)，通畅时是 (整条射线, None)。"""
    path = self.path_cells(piece)
    own = self.grid[piece.head[0]][piece.head[1]]
    for index, (row, col) in enumerate(path):
        other = self.grid[row][col]
        if other is not None and other != own:
            return path[:index + 1], self.pieces[other]
    return path, None
```

因为四个方向都被统一成增量对，所以**不需要写四份判断分支**：
朝上就是 `(-1, 0)`，朝右就是 `(0, 1)`，`while` 循环天然只沿一个方向推进，
边界由循环条件兜住，从根上避免了「向上判断时数组越界」这类经典错误。

**为什么挡路判定要放在棋盘层。** `path_to_blocker` 里有一句 `other != own`：
一支管道是好几格，它完全可能从自己箭头旁边绕过去，把自己算成阻挡的话它就永远飞不出去。

而且这里还藏着这一版最典型的一个 bug：**「挡路的那一格」不等于「挡路那支的箭头」**。
压在射线上的通常是它的**身子**，箭头可能在很远的另一头。界面上早先直接写
`path.index(blocker.head)` 来算红段画到哪，只要挡路那支的箭头不在射线上就会抛
`ValueError`（悬停到这类管道上就崩）。所以这个判断必须放在棋盘层、按格子归属来算。
后来画辅助线时同一个坑又踩了一次，详见第四节记录 12。

### 3.4 单一状态入口：逻辑和表现彻底分开

所有对棋盘的修改都必须经过 `Board.click(row, col)`，它返回一个 `ClickResult`
（`fly` / `blocked` / `empty` / `ignored`），并且带上被点的管道、挡路的管道和整条射线路径。
界面层拿到返回值后只做一件事：决定播哪个动画。

```python
path = self.path_cells(piece)
blocker = self.find_blocker(piece)

if blocker is None:                        # 前方无阻挡 -> 整条管道飞出
    for r, c in piece.cells:
        self.grid[r][c] = None
    self.remaining -= 1
    if self.remaining == 0:
        self.state = STATE_CLEARED
    return ClickResult(CLICK_FLY, piece, None, path)

self.hp -= 1                               # 前方有阻挡 -> 丢一颗心
if self.hp <= 0:
    self.state = STATE_FAILED
return ClickResult(CLICK_BLOCKED, piece, blocker, path)
```

注意飞出时要清的是 `piece.cells` **全部格子**，不是一格——一个「点中一格消掉一整条」的
操作就这么来的。这样测试可以完全绕过渲染直接验证规则，动画也永远不会反过来改状态。

### 3.5 飞出与撞击的表现

* **飞出**：`FlyOut` 让整条管道**沿自己的折线路径滑出去**，像贪吃蛇转弯的连续版——
  箭头先钻出去，拐弯顺着身体一路「流」到尾巴，全程连续插值、不是一格一格地跳。
  实现上是把各格中心连成折线（过箭头后沿箭头方向直线延长），每个折点沿路径
  前进相同的弧长 `advance`，每帧按新折点直接画两遍（描边 + 本色），
  不再走整张贴图的缓存——贴图是刚体，表达不了「弯折在移动」。
  `advance` 用 `progress ** 1.7` 做缓入，看起来像被抽出去一样越来越快；
  总弧长按「尾到箭头的弧长 + 箭头到视口出口的距离 + 0.9 个格子」算，保证彻底离场。
* **撞击**：`Impact` 动画做三件事——沿方向前冲 18% 格宽再弹回（`sin` 曲线）、
  垂直于前进方向做衰减抖动、管道泛红并向外扩散一圈红框。
  整个动画 0.36 秒，结束后自动从动画列表移除。
* **丢心**：`FloatingHeart` 把像素心复制成左右两半，每帧分开旋转、边倾斜边淡出往上飘，
  前 30% 时间保持不透明，避免玩家还没看清就消失。

### 3.6 生命值、得分与关卡难度

这一块是后期迭代出来的，我觉得是这次最有意思的部分。

**先定义「难」**。这个玩法有个容易被忽略的性质：点掉一支能飞出去的管道，
只会让其它管道的射线更空，所以**任何一步正确操作都不会把自己玩死**——
它不存在「顺序错误」，唯一会输的方式是点了一支其实被挡住的管道。
于是难度**只来自一件事：在棋盘上找出此刻哪些管道的箭头前方是空的**。

**难度分**因此定为：

```
难度分 = 管道数 × 1.6 + 棋盘格数 × 0.12 − 开局可点数 × 3.0      → 再映射成 1~5 颗星
```

刻意**不含生命值**：生命值现在是由难度分推出来的（见下），要是再把生命值算进难度分，
就成了「难度高 → 给的心多 → 难度算下来变低 → 星级跳回去」的循环。

**生命值按难度给**，因为越到后面越容易手滑：

```python
HP_BY_STARS = {1: 4, 2: 5, 3: 6, 4: 6, 5: 7}      # 越难容错越高
```

**得分按剩余生命值的比例折算**，而不是「每错一次扣固定分」：

```
基础分   = 星级 × 250
本关得分 = 基础分 × 剩余生命值 ÷ 生命值上限
完美奖励 = 一颗心都没丢时，再额外 +20% 基础分
```

为什么按比例：生命值上限逐关变大，固定扣分会让后面的关卡因为心多而显得无所谓
（第 9 关丢 1 颗心还剩 6 颗，扣的却和第 1 关一样多）。按比例折算则始终是
「这一颗心占本关全部容错的多大一份」，越到后面越宽容，和玩家直觉一致。
于是每关满分正好是「星级 × 300」，9 关合计 **8400 分**。

### 3.7 教学关、关卡总览与进度存档

**教学关**的引导要能**自愈**：玩家完全可以不按提示点。所以每一步在展示前都会和棋盘状态
对一次账——目标格子已经飞走了、或者这一步的前提（比如「它被挡住了」）已经不成立，
就自动跳到下一步，绝不会出现「让你去点一支已经不在棋盘上的管道」这种尴尬。
实现在 `Game.sync_tutorial()`。

教学关**不放进 `LEVELS`**，而是单独的 `TUTORIAL` 常量：它不计分、不占关卡编号、
不需要解锁，主菜单上有独立入口。这样编号就从第 1 关「初次拉弓」干净地开始，
玩家也不会把教学关误当成一道要拿分、要解锁的题。

**进度存档**用 JSON 而不是 `pickle`（原因见第四节记录 6）：

```json
{ "version": 2, "cleared": [0, 1, 2], "scores": { "0": 300, "1": 300 } }
```

解锁规则只认**从头连续通关的前缀**，实现就是在第一个没通关的关卡处 `break`——
跳着通关不算数，难度递进不会被绕开。存档升级到 version 2 加了 `scores` 字段，
读的时候用 `data.get("scores", {})`，老存档读进来就是「都没得分」，不会因为升级而丢进度。

### 记录 1：第 2 关摆出了死局

**我的要求**：设计 4 个难度递进的关卡，用文本布局表示，第 2 关要「有且只有一支箭能直接飞出去」，
用来教玩家「先找出口」。

**AI 提供**：直接给了 4 关布局。第 2 关长这样：

```
.....          (1,1) 的「>」被 (1,3) 的「v」挡住
.>.v.          (1,3) 的「v」被 (3,3) 的「<」挡住
.....          (3,3) 的「<」被 (3,1) 的「^」挡住
.^.<.          (3,1) 的「^」被 (1,1) 的「>」挡住
.....
```

**实际效果**：开局可点的棋盘数量是 **0**。四支箭头首尾相接围成一个环，互相指责，
谁都飞不出去——这一关是**无解**的。

**我的处理**：其实我当时也没一眼看出来，是写完校验脚本后报的警。顺着「谁挡住了谁」
捋一遍就明白了。修改办法很简单：把 `(3,3)` 的 `<` 挪到 `(3,4)`，
它左边依然是 `(3,1)` 的 `^`（保持阻挡关系不变），但不再挡在 `(1,3)` 的 `v` 下方了。

**这件事的价值**：它让我意识到**关卡不能靠眼睛验收**。后来我把「所有关卡必须可解」
直接写成了单元测试，布局一改就会被自动拦住。
（这一版关卡重做成弯曲管道之后，第 2 关已经换成了 13×9 的新布局，
但这条教训留到了今天：`validate_layout` 在导入时就拦非法形状，校验脚本与单测再各解一遍。）

### 记录 2：为什么用贪心判断关卡有解

**我的要求**：写一个脚本，能自动判断关卡能不能通关，并给出一个参考通关顺序。

**AI 提供**：反复扫描棋盘，把当前能飞出的管道全部消掉，直到不能再消；还有剩余就说明无解。

**实际效果**：跑起来完全正确。但我不太放心——「每次都消所有能消的」这种贪心，
会不会因为选择顺序不合适而漏掉真正的解？

**我的处理**：我补了一个证明，并把它写进了代码注释：

> 消除一支管道只会让其它管道的射线**变得更空**，永远不会让某条射线变得更堵。
> 也就是说「某支此刻能飞」这个性质具有**单调性**：此刻能飞，之后任何时刻都还能飞。
> 既然不会因为选择而失去任何机会，那么反复「消掉当前所有能飞的」就是完备的——
> 能全消掉就一定有通关顺序，卡住了就说明真的无解。

这条单调性还写成了测试（`test_solver_is_monotonic`）。另外我专门构造了一个**必然死锁**的
布局做反向验证，这个用例跑通之后我才确信校验脚本可信。

### 记录 3：`pygame.font.SysFont()` 在本机直接崩溃

**我的要求**：界面全中文，需要加载系统中文字体。

**AI 提供**：教科书式的写法 `font = pygame.font.SysFont("Microsoft YaHei", 32)`。

**实际效果**：在这台 Windows 机器上，这一行**直接抛异常**：

```
File "pygame\sysfont.py", line 82, in initsysfonts_win32
    if splitext(font)[1].lower() not in OpenType_extensions:
TypeError: expected str, bytes or os.PathLike object, not int
```

原因是 pygame 枚举注册表里的字体项时碰到了不是字符串的条目，属于 pygame 2.6.1
在特定 Windows 字体环境下的兼容问题——**这是只有真的跑起来才会暴露的错误**。

**我的处理**：不再依赖 `SysFont` / `match_font`，改成自己按路径找字体文件，
依次尝试 `msyh.ttc` / `simhei.ttf` / `Deng.ttf`（Linux 和 macOS 各给一条路径），
都没有就退化为默认字体并在控制台警告。这样跨平台都能用，找不到字体也不会崩。

### 记录 4：测试用例首轮 4 个失败

**我的要求**：按作业给的 T01–T06 写自动化测试。

**AI 提供**：23 个用例，逻辑看着都对。

**实际效果**：第一次运行 **4 个失败**，原因分成两类，都不是源码的问题，而是测试自己写错了：

第一类，**测试关卡的数量写错了**（`AssertionError: 2 != 3`、`3 != 4`）。
测试布局里其实只有 3 支，但断言按 4 支写——AI 把先前另一个草图的数量记串了。

第二类，**测试辅助函数把「已经飞出去的」当成了「被挡住的」**：

```python
def blocked_arrow(self, board):
    for arrow in board.arrows:
        if not board.can_fly(arrow.row, arrow.col):
            return arrow        # BUG：飞出去之后 can_fly 也是 False
```

`board.arrows` 保存的是**关卡初始的全部箭头**（用于重开时复位），飞出去之后
它依然在列表里，但已经不在 `grid` 上了，于是 `can_fly` 返回 False，辅助函数就会误判，
结果点击时命中空格、根本不扣生命值，测试自然失败。

**我的处理**：断言数值按实际布局修正；辅助函数加一句「必须还在棋盘上」的过滤。

> 顺带一提：这是**首版**测试的数量。后面加了关卡总览、逐关解锁、教学关、生命值、得分、
> 计时、提示、辅助线、缩放、双主题，以及两次整体重做（界面 + 棋子模型）之后，
> 用例扩到了 **222 个**，最终结果见第六节。

**这件事的价值**：测试失败不等于源码有 bug，也可能是测试自己在说谎。
两次都不是改游戏，而是改测试——但**前提是你得先看懂源码到底怎么运行的**，
这也正好说明「AI 生成的代码必须自己理解」不是一句空话。

### 记录 5：让 AI 生成关卡，结果它挑出来的全是最简单的

**我的要求**：再加几关，难度要递增，而且每一关都必须能通关。
随机撒很容易撒出无解布局，所以我要求 AI 写一个生成器，用已有的求解器当验收。

**AI 提供**：`tools/generate_levels.py`，思路是「随机撒 → 用贪心求解器筛掉无解的 →
按难度分排序取前几名」。

**实际效果**：筛出来的关卡确实都能通关，但**全部是开局几乎每支都能飞出去的松布局**。
10×10 摆 30 支，开局可点 24 支——玩家随便点都能过，难度根本谈不上。
翻代码才发现，排序那行方向写反了：难度分里「开局可飞行数」是负权重，
我却按升序取前几名，等于专门挑最简单的。

**我的处理**：先停下来想清楚一件事——**这个游戏到底难在哪里**（就是 3.6 节那段推理）。
想通之后，生成器换成两条新做法：

* **逆向构造**：把「消除顺序」倒过来当「放置顺序」，放置时只要求「新管道箭头正前方
  没有已放置的管道」，这样放置顺序的逆序天然就是一个合法通关顺序，布局**必然可解**，
  连事后筛选都不需要；
* **阻挡偏好**：维护一张 `seen` 表，记录每个格子「被多少支已放置管道的射线覆盖」，
  放置新管道时优先选这些格子——新管道正好落在老管道前方，老管道就得等它先走。
  这张表让判断「这格会不会挡住别人」变成 O(1)，不然每放一支都要重扫全盘。

结果：同样是 10×10 / 30 支，开局可点数从 24 支压到 **7 支**，玩起来才真的需要一行一行地扫。

**这件事的价值**：排序方向写反是个很低级的错误，但更值得注意的是——
**AI 不会觉得「挑出来的关太简单」有什么不对**，因为它没有「这一关玩起来应该是什么感觉」的直觉。
「什么叫做难」这件事必须由人先定义清楚，再翻译成能写进代码的指标。

### 记录 6：进度用 pickle 存，看着能用其实是个雷

**我的要求**：记录玩家已经通关到第几关，没通关前面就不让玩后面；关掉游戏再打开，进度还在。

**AI 提供**：把已通关关卡的下标集合 `pickle` 到一个文件里，启动时 `pickle.load` 读回来。

**实际效果**：能跑。但有两个问题一看就心里发毛：

1. `pickle` 是二进制，存档出问题时**打不开也看不懂**；
2. 只要文件损坏（比如写到一半断电），`pickle.load` 会直接抛异常，
   **整个游戏在启动时就崩掉**——对一个要交给老师演示的作业来说这是致命的。

**我的处理**：

* 换成 JSON：存档打开就是 `{"version": 2, "cleared": [0, 1, 2], "scores": {...}}`，一眼能看懂；
* 加容错：读失败当作空进度，写失败只在控制台警告一次，游戏照常能玩。
  这是一个有取舍的决定——严格报错更「正确」，但演示场景下「能继续玩」更重要；
* 把解锁规则从界面代码里抽出来，放到不依赖 pygame 的 `progress.py`，
  于是「通关一关才解锁下一关」这条规则可以用普通单测覆盖，不必为了测一条 `if` 去创建窗口。

**这件事的价值**：AI 给出的方案经常是「功能可用」就停了，**异常路径完全是空白**。
凡是会落盘的东西，都要自己问一句：文件损坏了会怎么样？目录没写权限会怎么样？

### 记录 7：「塞得越多越难」，实测正好相反

**我的要求**：后面几关再难一点。

**AI 提供**：很自然的建议——把棋盘放大，再往里多塞，密度上去难度就上去。

**实际效果**：放大棋盘确实有用，但**提高密度完全没用，甚至反着来**。
实测数据很反直觉：

| 棋盘 | 管道数 | 占格率 | 开局可点数 |
| --- | --- | --- | --- |
| 9×9 | 30 支 | 0.37 | 7 支 |
| 9×9 | 54 支 | 0.67 | **18 支** |

塞进去的管道多了将近一倍，开局能直接点的反而从 7 支涨到 18 支，比稀疏时还简单。

**原因是我想了一会儿才想明白的**：**贴着棋盘边缘、朝着棋盘外的管道，它的射线长度是 0，
永远能飞**。密度一高，剩下的合法放置位置几乎只剩这一类（它们永远合法），
于是整个布局退化成「一大半开局就能点」的松局面。

**我的处理**：给生成器补两条：

1. **排除空射线候选**：除最后一步外，一律避开射线为空的候选位置；
2. **打分里加上「自己射线的长度」**：只优化「能挡住别人」而不优化「能被别人挡住」是不够的。

**这件事的价值**：AI 给的方案在**逻辑上**都没错——多放确实会让棋盘更挤。
错的是它没有「玩起来是什么感觉」这一层判断，而这层判断只能靠自己跑一遍数据才能发现。
**能算的就要算，不要凭感觉。**

### 记录 8：配色来回改了两轮，最后靠「把不好看变成数字」收场

**我的要求**：第一轮是「关卡里的颜色有点单调，想让它看起来丰富一些」；
后来又补了一句更具体的：「不同颜色混在一起，而不是相同颜色的管道扎堆」。

**AI 提供**：

* 第一版：给每个方向配 4 档明暗变体，用坐标挑档（`(row * 3 + col * 5) % 4`）；
* 第二版（这一版）：颜色改成从 12 色糖果调色板里取，再保证**相邻不同色**。

**实际效果**：

* 第一版的同向相邻占比确实降下来了，但**新的问题出现了**——同一方向内感知亮度跨度到了
  71~79（浅到深差三倍），看起来不是「丰富」而是「杂乱」。于是我又得回头要求「统一」；
* 第二版（糖果色 + 相邻不同色）是**照着参考画面重做**的：同色管道挨在一起会连成一大片、
  数不清有几支，所以约束的是「相邻不许同色」，而不是「一个方向一个颜色」。

**我的处理**：分两步走，而且第一步是**先量化**：

* 写脚本统计「相邻且同色的管道对占比」和「同色 4-邻接连通块的最大格子数」，
  发现第 7 关相邻同色对占到一半以上、最大同色块 6 格——确实是扎堆，不是我的错觉；
* 去掉方向色，改成 12 色糖果随机取，再用**贪心染色**避开相邻同色
  （挨个处理，挑一个邻居没用过的颜色），并把这条约束写成测试
  `test_no_two_adjacent_pieces_share_a_color_in_any_level`，**九个关卡逐个检查**。

**这件事的价值**：用户说「不好看」时，别直接开始调色——先把这句话变成一个**可测量的数字**
（相邻同色对占比、亮度跨度），改完再拿同一个数字验证，否则只是在凭感觉换配色。
另外也说明**用户两次看似矛盾的要求（先「太单调」后「要统一」）其实说的不是一回事**：
前者指同类元素连成一整块，后者指同类元素之间深浅不一，两边都要满足。

### 记录 9：加完新功能，回归挂了两个用例

**背景**：加上关卡总览、逐关解锁、教学关之后跑一遍回归，挂了 2 个用例。两个都挺有意思。

**坑 A：`test_t06_restart_mid_game` 报「本关没有找到被挡住的管道」**

测试本身没写错，是**关卡数据变了**：教学关被插到了第 1 关，而它只有 3 支，
消掉一支之后剩下两支都畅通，再也制造不出「点击被挡住的管道」这个场景。

改法是把 T06 挪到第 2 关——它同时存在能飞的和被挡的。顺带意识到一个更根本的问题：
**测试里写「第 1 关」就是一种隐式耦合**，一旦关卡表调整就会连带失效。
所以改成按关卡名查下标，并把「这一关要有被挡的管道」写成辅助函数里的断言。

这种漏写人眼一扫很容易放过，测试一秒钟就抓到了。

**还有两个只有看图才能发现的问题**

跑完测试全绿之后我照例重新生成截图，一张一张看，发现两处：

* **提示气泡会跟着玩家进入关卡**——切换场景时没有清掉气泡计时器；
* **教学关的高亮环把管道压暗了**——高亮环的呼吸填充画在管道之后，
  半透明的琥珀色盖在管道上，看着像蒙了一层灰。改成底色画在管道下方、只有外环画在最上层。

这两个都不是逻辑错误，**测试也测不出来**——是靠生成截图后逐张检查发现的。

**这件事的价值**：自动化测试能守住「逻辑对不对」，守不住「看起来对不对」。
一个可运行 + 可测试 + **有截图可复查**的项目，验收时才算闭环。

### 记录 10：照着参考图重做界面，返工全卡在「话没说清」

**我的要求**：找了一张同类游戏的截图当参考，让 AI 把界面改成那个样子——
纯色背景、棋盘只留点阵（不要卡片格子）、棋子做成**糖果色的胖管子**、
顶部居中一条信息栏（关卡名 / 计时 / 生命值 / 剩余管道数 / 得分）、底部一排工具按钮。

**AI 提供**：一次给全了配色常量、管道绘制函数、图标集和整块 HUD 布局。
第一版跑起来大方向是对的，但截图逐张看下来，还是有三处不对味：

1. **棋盘还留着卡片格。** 参考图是纯色点阵，AI 却沿用了上一版的「星空背景 + 带边线的方格」。
   原因是我第一次描述时只说了「棋子要像管子」，没提棋盘本身要改——
   等我把话说到「每格只留一个半透明白点、不要边框」，它才一次改到位。
2. **教学关的提示条被底部工具栏压掉了。** 新加了工具栏，却没有把这块高度从棋盘区域里预留出去。
3. **三个方向色看着不齐。** 分开看都挺好看，摆在一起就有一支明显偏亮，「胖管子」的质感反而散了。

**我的处理**：

- 棋盘重做成**点阵**：每格画一个约 26/255 透明度的白点；
  已经走过的路径只铺一层很淡的色块，并且**向内缩**——否则一条路径连起来像几块污渍。
- 布局不再手写坐标，改成**从常量推导**：信息栏高度、工具栏高度先进布局计算，
  再交给绘制层用；顺手补了一条「各分区矩形互不重叠」的用例。
- 亮度不靠眼睛调，改成**算亮度**（`0.299R + 0.587G + 0.114B`）并**写成断言**，
  以后谁再动配色，只要破坏这个范围，测试立刻变红。
- 另外修掉了标题里「教学关」重复出现两次的小毛病。

**这件事的价值**：做界面最费时间的不是写绘制代码，而是**把「我要什么」说清楚**。
我说「棋子要像管子」，AI 就只改了棋子，棋盘还是老样子；
我说「每格只留一个点、不要边框」，它一次就到位。
**一句模糊的需求，换来的是一整轮返工**——这是这一轮我最大的体会。

### 记录 11：把「一格一支箭头」改成「占多格的弯曲管道」

**我的要求**：参照画面里根本不是「一格一个箭头」，而是一条**蜿蜒的管道**，
末端才有一个箭头。我要求把棋子模型改过来，并且**保持规则不变**（还是「箭头前方空就能飞」）。

**AI 提供**：管道模型的初稿——把棋子从「一个坐标 + 方向」换成「一串相邻坐标 + 一个方向」，
渲染时沿着这串坐标画一条圆角粗线，末端补一个三角。

**实际效果**：渲染层大改之后**规则层和工具链全线失效**：

* 旧的规则代码到处在读 `board.arrows`、`arrow.row`、`arrow.col`、`arrow.delta`，
  这些概念在管道模型里根本不存在；
* 关卡数据原来是 ASCII 布局（`.>v<^` 一格一个字符），现在要写成 `行,列 方向 路径`；
* 六个工具脚本（校验 / 生成 / 挑选 / 截图 / 动图）全部跑不起来；
* 旧的 222 个测试里有一大批直接 `AttributeError`。

**我的处理**：

* **新建 `pieces.py`**，把「解析写法 / 格式化 / 射线 / 布局校验 / 相邻染色」这些纯几何的活儿
  全部收拢进去，`board.py` 只保留「点击 → 判定 → 改状态」这条主干；
* 把「挡路判定」从「哪个箭头」改成「**哪个格子属于别的棋子**」——
  因为一支管道占好几格，压在射线上的通常是它的身子；
* 关卡数据全部重写成管道写法，并用生成器重新出一遍题；
* 工具脚本按新 API 重写，测试按新 API 重写（这一步的工作量最大）。

**这件事的价值**：**「换个表示法」从来不只是换个数据结构。**
AI 改得很听话——你让它把箭头画成管子，它就把箭头画成管子；
但「所有依赖旧表示法的代码都会失效」这件事它不会主动告诉你。
真正的工作量在**连锁影响**上，而判断连锁影响的范围是人的活儿。
这也是为什么我坚持「规则模块不许 import pygame」：
正因为它不碰界面，这次重做时我才能确定**只改数据的表示、不改规则的正确性**。

### 记录 12：辅助线斜穿整个棋盘

**背景**：加完「辅助线」功能之后，截图逐张检查时发现有几条线明显不对——
它们斜着穿过整个棋盘，连到一个跟箭头方向完全无关的格子上。

**原因**：画线的时候要决定「线画到哪为止」。AI 写的代码是这样的：

```python
path, blocker = self.board.path_to_blocker(piece)
if blocker is not None:
    return start, self.cell_center(*blocker.head)     # BUG
```

`blocker.head` 是**挡路那支管道的箭头**。上一版棋子只有一格，箭头就在那一格，
所以这个写法是对的；改了管道模型之后，一支占好几格，**压在射线上的通常是它的身子**，
它的箭头可能在很远的另一头——于是线就从箭头方向斜着连过去了。
更糟的是，如果那支管道的箭头恰好不在射线上，`path.index(blocker.head)` 会直接抛
`ValueError`，悬停到这类管道上游戏就崩。

**我的处理**：改成用「**射线上被占的那一格**」，也就是 `path_to_blocker` 返回的路径最后一项：

```python
def guide_segment(self, piece):
    """这条辅助线的两个端点；管道已经飞走时返回 None。"""
    ...
    path, blocker = self.board.path_to_blocker(piece)
    if blocker is not None:
        return start, self.cell_center(*path[-1])      # 射线上被占的那一格
    return start, {方向: 棋盘边}[piece.direction]
```

顺手把它抽成一个独立方法 `Game.guide_segment()`，并补了 3 条几何测试：

* `test_guide_segment_is_parallel_to_the_arrow`——用**叉积为 0** 卡「必须和箭头共线」，
  用点积卡「长度和射线一致」；
* `test_guide_segment_ends_inside_the_blocking_cell`——被挡时终点必须落在那一格的矩形里；
* `test_guide_segment_disappears_with_the_piece`——管道飞走之后线也要消失。

> 写这几条测试时还踩了一次浮点：朝棋盘外、射线长度为 0 的管道，理论上线长应该是 0，
> 但两个端点各自取整之后算出 `-0.5`，被 `assertGreater(length, 0)` 拦下来了。
> 改成「射线为空时断言 `abs(length) <= 1`（给个浮点余量），非空时才要求严格大于 0」。

**这件事的价值**：这个 bug **不是靠读代码发现的，是靠看图发现的**——
测试全绿、逻辑「看着对」，只有把它画出来才知道线歪了。
而它的根因是**同一个概念在上下文变了之后变味了**：
`blocker.head` 在「一格一支」的世界里等于「挡路的那一格」，在管道世界里不再等于。
把这种判断从界面搬到棋盘层、再抽成一个有名字的方法、最后用几何量卡住，
才算真的修好了而不是绕着它走。

### 记录 13：演示 GIF 有 8 MB

**背景**：录完演示动画，文件有 8000 KB，网页上加载要等很久，明显不正常。

**原因**：我在拼帧的时候给每帧加了 `disposal=2`（每帧先把整块画布清成背景再画）。
本意是「免得上一帧残影留下」，但 Pillow 的行为是：一旦发现帧不是完全透明，
就**放弃帧间差分、每帧整幅写一遍**。2400×576 的整幅编码写了 184 次，体积自然爆炸。

**我的处理**：

* **去掉 `disposal=2`**，让 Pillow 走默认的 `disposal=0`（帧间差分），只写变化的像素块；
* 等比缩到 360×576（`SCALE = 0.6`）；
* 调色板降到 128 色；
* 中段用「快进录」：按住解法把几步一条过，只录关键的那几个转折。

改完体积从 8000 KB 降到 **2300 KB**，画质肉眼看不出差别。

**这件事的价值**：GIF 体积不是「压一压」就行的，得先搞清**编码器到底在做什么**。
我一开始也想当然地以为「加 disposal 是清理，清了更干净」，
实际读了 Pillow 的 `GifImagePlugin` 源码才明白它把帧间优化给关掉了。
**猜优化的方向，往往正好猜反。**

### 记录 14：飞出动画从「整条平移」改成「沿路径滑出」

**背景**：管道版做完后自己试玩，总觉得飞出的那一瞬间不对劲——
管道是一张刚体贴图，朝箭头方向整体平移，拐弯的部分是**横着蹭**出去的，
不像「钻出去」，更像「被拖走」。

**我的要求**：飞出的时候像贪吃蛇转弯那样，箭头先钻出去，拐弯顺着身体传到尾巴；
但不要一格一格地跳，要顺滑。

**AI 的方案**：把各格中心连成折线，过箭头后沿箭头方向直线延长；
飞出时**每个折点沿路径前进相同的弧长**，每帧按新折点位置直接重画管道。
因为每点走的弧长一样，弯折会连续地「流」过去——这正是贪吃蛇转弯的连续版。
缓入沿用 `progress ** 1.7`，加速感还在。

**踩的坑**：

* 原来的飞出画的是**整张贴图**（缓存好的 Surface），刚体表达不了「弯折在移动」，
  所以动画那零点四秒必须绕开缓存直接画——描边、本色两遍照旧，观感才和静止时一致；
* 总滑行弧长不能照搬旧算法：旧的是「最靠后的边到视口出口」的直线距离，
  新的要加上「尾巴到箭头的弧长」，不然长管道滑不完就停在中途；
* 弧长落点的边界（正好等于折线总长时）先写了 `<=`，数组越界，测试当场抓住。

**验证**：L 形管道在半格、一格半、两格、两格加 25 像素四个时刻，
尾巴的位置必须正好落在原始路径的对应点上（`test_fly_out_tail_follows_the_bend`），
再加无头渲染中间帧肉眼确认弯折确实在流。

**这件事的价值**：表现层的改动也可能牵动几何，**「顺滑」两个字背后是弧长参数化**——
把动画量从「位移向量」换成「沿路径的弧长」，贪吃蛇的效果就自然出来了。

**满分合计 8400 分**（9 关合计 285 支管道）。

难度曲线的做法是**先量、再插**。九个关卡的难度分是
`23.2 / 32.8 / 37.0 / 49.3 / 58.7 / 80.8 / 91.4 / 106.7 / 120.8`，
一路单调递增。三条性质都写成了断言：棋盘只许变大、管道只许多、
开局可点数不许增加、星级不下降。

**难度轴这一版换过一次，理由值得记一笔。**

上一版是「棋盘冻结在 9×9，之后靠提高密度加难」。
这一版重做成管道之后，这条轴**不成立了**，因为：

* 一支管道占 4~9 格，密度不可能像单格棋子那样往上堆；
* 真正变难的原因变成了「**要扫的射线变长变多**」——棋盘越大、管道越长、交叉越多，
  一眼能扫完的部分就越少。

所以现在的做法是：棋盘从 11×8 一路放大到 26×18，管道从 21 支加到 46 支，
而**开局可点数从 7 支一路收到 3 支**。最后这一项才是真正决定手感的那一项——
它就是上一版留下的那条经验，没变。

  提交前又把**飞出动画从整条平移改成沿路径滑出**（见第四节记录 14）。
  视觉上的「差不多」和「看着舒服」之间差距很大，而「换个表示法」的代价比预想的大得多。

  ①手摆的布局出现无解，②生成的布局全是简单关，③提高密度反而更简单，
  ④同色扎堆；改成管道模型之后**九个关卡又全部重做了一遍**。
  这一项也是收获最大的。
* **测试与修改超支**（+2.0）：预估时只想着作业要求的 T01–T06，
  实际每加一个功能（解锁、教学关、生命值、得分、计时、提示、辅助线、缩放、双主题）
  都要补回归用例；两次整体重做又让一批测试直接失效，只能跟着 API 一起重写。
  最后涨到 222 个。不过这些用例也确实抓到了真问题（清空进度没有复位、
  教学关插到第 1 关导致 T06 失效、辅助线几何算错）。
* **路径与碰撞逻辑持平**（0.0）：这是最核心的算法，但把四个方向统一成
  `(行增量, 列增量)` 之后，循环只有两份，边界问题从根上避免了。
  「先把数据结构想清楚再写代码」在这里省下了大量时间——
  也正因为规则层干净，改管道模型时才能确定「只改表示、不改正确性」。
* **文档撰写略超**（+1.0）：博客不只是记录，还要挑出「AI 给了什么、我改了什么」的真实细节；
  而且每次重做都要把 README、博客、测试报告、检查清单四份文档一起同步，
  这部分比写使用说明费时间，但这些细节恰好是最有价值的部分。

## 九、心得体会

1. **AI 写代码很快，但「验收」只能靠自己。** 这次真正花时间的不是写代码，
   而是把每个环节真的跑一遍：一跑就发现字体崩溃、一跑就发现第 2 关无解、
   一跑就发现 GIF 有 8 MB。代码看起来再对，不运行就不算数。

2. **能自动校验的东西一定要自动校验。** 「关卡必须可解」这件事，用眼睛看 4 个布局也许能看出来，
   但关卡一旦扩到 9 个就必然出错。写成求解器 + 单元测试之后，改布局完全不慌。

3. **让 AI 给出「可测试的结构」，比让它一次写对更重要。** 把规则模块和 pygame 彻底隔开之后，
   规则测试从「要开窗口、要模拟鼠标」变成「三行代码断言一个状态」，效率差了一个数量级。
   更关键的是：**后来把棋子模型整个换掉时，正是这层隔离让我能确定「改的只是表示法，
   规则的正确性没动」**——如果规则和渲染搅在一起，那次重做根本不敢做。

4. **测试失败不一定是源码的问题。** 首轮 4 个失败全是测试自己写错了，
   但排查过程必须回到源码去看 `grid` 和 `arrows` 的区别——
   这也是为什么「必须理解自己提交的代码」。

5. **「难」这件事得由人来定义，而且要用数据验证。** 让 AI 生成关卡时，它给的关卡逻辑上都成立、
   都能通关，但没有一关是「难」的——因为它没玩过游戏，不知道什么叫难。
   我先想清楚「这个游戏唯一会输的方式是点错一支被挡住的管道」，
   才能把「难」翻译成「开局可点数要少」这条能写进代码的指标。
   更反直觉的是「塞得越多越难」——这一条**想当然是错的**，只有真的跑数据才会发现。

6. **「换个表示法」从来不只是换个数据结构。** 把「一格一支箭头」改成「占多格的弯曲管道」，
   听起来只是渲染上的事；实际上规则代码、九个关卡、六个工具脚本、两百多个测试全部要跟着改。
   AI 会很听话地把你说的那部分改好，但**它不会告诉你连锁影响有多大**。
   判断影响范围、决定哪些要重写、哪些能复用，是人的活儿。

7. **AI 的方案经常「功能可用」就停了，异常路径是空白。** `pickle` 存档那件事就是典型：
   正常运行完全没问题，但存档一损坏游戏就起不来。凡是会落盘、会联网、会读外部数据的地方，
   都要自己追问一句「出错会怎么样」。

8. **测试全绿不等于做完了。** 有好几次用例全过，但截图一看就发现
   提示气泡跟着进了关卡、教学高亮把管道压暗了、**辅助线斜穿整个棋盘**。
   逻辑正确和看起来正确是两件事，所以我把「自动生成截图和 GIF」也做成了项目的一部分，
   每次改完都过一眼。这一版最典型的那个 bug（辅助线画歪）就是**看图看出来的**，
   测试当时是全绿的。

9. **过程记录本身就是产出。** 这次踩的坑（无解关卡、生成器排序写反、密度陷阱、
   配色来回改、管道重做、GIF 体积）比最终代码更有价值——它们说明「AI 辅助开发」
   不是把需求丢给 AI 就完事，而是要人一直站在中间判断、验证、纠偏。
   这也让我意识到自己最缺的其实不是写代码的能力，
   而是**把模糊的直觉翻译成可验证指标**的能力。

## 十、如何运行

```bash
git clone https://github.com/zsx123456/one-arrow-after-another.git
cd one-arrow-after-another
pip install -r requirements.txt
python main.py
```

第一次运行会直接落在开始界面。点「教学关」可以先熟悉规则，点「开始游戏」直接进第 1 关。
此后每次启动都会读取项目根目录的 `progress.json`，接着上次的进度继续
（这个文件已经加进 `.gitignore`，属于本机状态，不会上传）。
想从头再来就在「设置」面板里点两次「清空进度」。

详细的环境说明、操作方式和常见问题见仓库的 `README.md`；
完整的测试日志、关卡校验输出和每一关的参考通关顺序见 `docs/test-report.md`。
