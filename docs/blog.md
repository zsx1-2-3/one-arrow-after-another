### 1.9 会动的背景

底色不是一块纯色，是**四层动效**叠出来的：

* **极光带**：6 条斜向柔光带缓缓往下流过（9~22 像素/秒，一条走完要一分多钟），
  是「画面活着」最主要的来源；
* **漂移光晕**：两团压得很暗的柔光沿李萨如曲线游走，几乎看不出在动，但画面不再是死的；
* **浮尘**：30 个小光点缓慢上浮、左右轻摆、明灭呼吸，飘出上边就回到下边；
* **流星**：隔 12~26 秒划一颗，尾巴由十个由亮到暗的小光斑拼出来。

亮度整体压得很低——**背景是衬托、棋盘上的箭头才是主角**。
所以游戏界面里光带浓淡只取菜单的 45%、浮尘从 30 个减到 14 个、流星间隔也拉长了。
日间主题则是另一套：底色是浅的，加法光只会糊成白斑，
于是同一张贴图改用**减法**叠加，极光带就成了「云影缓缓飘过」。

## 二、项目介绍

### 2.1 游戏规则

棋盘上散布着许多**箭头**。一支箭头是一条占若干格的**折线**，末端长着一个箭头，
朝向「上 / 下 / 左 / 右」四个方向之一。玩家点击某支箭头的**任意一格**：

* 它**箭头**正前方那条射线上**没有别的箭头**：整条箭头沿自己的方向飞出棋盘并被消除；
* 射线上**有别的箭头**：它不会消失，前冲一下再弹回、抖动、泛红，**丢掉一颗心**；
* 清空本关全部箭头即通关，剩下的心越多，本关得分越高；
* 心用光则本关失败，可以重新开始。

### 2.2 界面设计

一共五个画面：**开始界面**、**关卡总览**、**游戏界面**、**结果面板**（通关 / 失败 / 全部通关 /
教学结束，都是叠在游戏界面上的半透明面板）、**设置面板**；
教学引导是游戏界面的一种模式。

游戏界面自上而下分成**三块**：**顶部信息栏 / 棋盘 / 底部工具栏**。

* 信息栏上一行是齿轮（设置）、昼夜开关、关卡标题与右侧胶囊「关卡总览」；
  下一行把**计时、生命值、剩余箭头、本关得分**四组信息横排并**整体居中**。
  心数会随关卡变化（4~7 颗）、得分位数也会变，早期用一串写死的 x 坐标，
  每加一点内容都要人工核算会不会压住；现在先量出真实字宽再居中，内容怎么变都不会撞上。
* 棋盘**不画每一格的底框**，只有一片极淡的点阵。这个玩法的难度来自「在一堆箭头里
  找出能点的那支」，几十个空方框会让视线一直被拽住——那是「乱」不是「难」。
* 底部工具栏：左边圆钮「提示」、中间缩放滑杆与百分比、右边圆钮「辅助线」，
  圆钮下面各标一行名字，开关打开时圆钮和字一起变蓝。

配色上，箭头是一条**圆角粗箭头**，末端一个三角箭头，颜色取自一组 12 色糖果色；
但**相邻（上下左右）的两支箭头不允许同色**——同色箭头挨在一起会连成一片、数不清有几支，
所以 `pieces.assign_colors` 用贪心染色避开了这件事。

两套主题（顶栏那个月亮 / 太阳开关切换）：`night`（深色，默认）和 `day`（浅色）。
两套配色的键名完全一样，切主题就是把另一份值写到同一批常量上，
界面代码一行都不用改。

## 三、实现思路

### 3.1 技术选型与模块划分

选 Pygame 的理由很直接：动画和逐帧控制是它的主场；用 Surface 缓存可以把
「一条箭头的形状」画一次就反复复用；而且它**无头运行方便**——
把 `SDL_VIDEODRIVER` 设成 `dummy` 就能不开窗口批量出截图、跑测试。

我先让 AI 帮我拆了一遍模块，得到的是「一个几百行的 main.py 里什么都有」。
这个方案能跑，但没法测——规则逻辑和 `pygame.display` 搅在一起，写测试就得先开窗口。
所以我要求按下面这种方式重做，核心原则是**规则模块不许 import pygame**：

```
game/
├── config.py    全局配置：窗口尺寸、布局常量、两套主题配色、字体路径、动画参数
├── pieces.py    棋子模型：折线箭头、方向、射线、布局校验、相邻不同色
├── board.py     棋盘规则：点击 / 路径检测 / 飞出 / 生命值 / 胜负判定（纯 Python）
├── levels.py    关卡数据：箭头写法 + 教学步骤 + 难度评级 + 生命值表 + 校验
├── scoring.py   得分规则（纯函数）
├── progress.py  解锁规则与存档（纯 Python）
├── ui.py        绘图工具：字体、文字折行、按钮、滑杆、图标、像素心
├── anim.py      动画：整条箭头飞出、撞击抖动、飘字、心碎
├── bgfx.py      动态背景
└── app.py       游戏主体：场景状态机、事件分发、渲染
```

收益非常明显：`board.py` / `pieces.py` / `progress.py` / `scoring.py` 都可以用纯逻辑测试覆盖，
跑一次不到 0.1 秒；关卡是否有解能脱离游戏单独验证；界面改版不会碰到规则代码。

> 顺带一提，`pieces.py` 是**这一版才拆出来**的。上一版棋子是「一格一支箭头」，
> 方向、颜色、坐标都能塞进 `board.py`；改成占多格的弯曲箭头之后，
> 「解析写法 / 校验布局 / 算射线 / 分配颜色」这些几何活儿有 240 多行，
> 再和棋盘规则混在一起就没人看得懂了，于是单独成模块。

### 3.2 箭头、方向和关卡怎么表示

**方向**用两个东西表示：一个字符 + 一个增量对。字符用于读写关卡，增量对用于算法。

```python
DIRECTIONS = {"up": (-1, 0), "down": (1, 0), "left": (0, -1), "right": (0, 1)}
DIR_CHARS = {"^": "up", "v": "down", "<": "left", ">": "right"}
SEG_CHARS = {"U": "up", "D": "down", "L": "left", "R": "right"}
```

把四个方向统一成 `(行增量, 列增量)` 是这一版最关键的设计决定，理由在 3.3 说。

**一支箭头**就是一行字符串：`行,列 方向 路径`。

```
"4,6 > D3R2"     从第 4 行第 6 列出发，箭头朝右，
                 箭头先向下 3 格、再向右 2 格，共 6 格
```

**箭头在路径的末端**——也就是最后经过的那一格。路径必须逐格相邻、不能和自己交叉，
而且**最后一段必须和箭头方向一致**（不然画出来的箭头会歪在拐角上）。

```python
Level(
    name="交叉路口",
    hint="开局能点的很少，先找朝外的",
    max_hp=4,
    rows=13, cols=9,
    specs=(
        "2,0 > R2",
        "0,8 ^",
        # ...
    ),
)
```

写法由 `pieces.parse_piece` 解析，宽进严出：路径段可省略（`"5,0 <"` 就是只占一格朝左的短箭）、
可小写、多余空格会被折叠。**这里踩过一个坑**：不能对整串调用 `upper()`——
方向字符里的 `v`（向下）大写之后会变成 `V`，而方向表里认的是小写 `v`，
于是所有朝下的箭头都会解析失败。所以只把「路径段」那一段提出来大写，方向字符单独按小写查表。
测试里专门有一条 `test_parse_downward_piece_is_not_broken_by_upper` 钉住这件事。

`pieces.validate_layout` 在关卡导入时就做校验：都在盘内、互不重叠、逐格相邻、不自交、
末端一段与箭头方向一致、**射线不能穿过自己的身体**（否则这支箭永远飞不出去）。
**非法数据在构造时就报错**，不会等到画到屏幕上才发现。

### 3.3 路径检测（核心算法）

这是整个游戏的算法核心，两段代码就够了：

```python
def ray(self, rows, cols):
    """从箭头出发、沿箭头方向直到棋盘边界的格子（不含箭头自己）。"""
    d_row, d_col = self.delta
    row, col = self.head[0] + d_row, self.head[1] + d_col
    cells = []
    while 0 <= row < rows and 0 <= col < cols:
        cells.append((row, col))
        row += d_row
        col += d_col
    return cells

def path_to_blocker(self, piece):
    """返回 (射线上到挡路那支为止的格子, 挡路的箭头)，通畅时是 (整条射线, None)。"""
    path = self.path_cells(piece)
    own = self.grid[piece.head[0]][piece.head[1]]
    for index, (row, col) in enumerate(path):
        other = self.grid[row][col]
        if other is not None and other != own:
            return path[:index + 1], self.pieces[other]
    return path, None
```

因为四个方向都被统一成增量对，所以**不需要写四份判断分支**：
朝上就是 `(-1, 0)`，朝右就是 `(0, 1)`，`while` 循环天然只沿一个方向推进，
边界由循环条件兜住，从根上避免了「向上判断时数组越界」这类经典错误。

**为什么挡路判定要放在棋盘层。** `path_to_blocker` 里有一句 `other != own`：
一支箭头是好几格，它完全可能从自己箭头旁边绕过去，把自己算成阻挡的话它就永远飞不出去。

而且这里还藏着这一版最典型的一个 bug：**「挡路的那一格」不等于「挡路那支的箭头」**。
压在射线上的通常是它的**身子**，箭头可能在很远的另一头。界面上早先直接写
`path.index(blocker.head)` 来算红段画到哪，只要挡路那支的箭头不在射线上就会抛
`ValueError`（悬停到这类箭头上就崩）。所以这个判断必须放在棋盘层、按格子归属来算。
后来画辅助线时同一个坑又踩了一次，详见第四节记录 12。

### 3.4 单一状态入口：逻辑和表现彻底分开

所有对棋盘的修改都必须经过 `Board.click(row, col)`，它返回一个 `ClickResult`
（`fly` / `blocked` / `empty` / `ignored`），并且带上被点的箭头、挡路的箭头和整条射线路径。
界面层拿到返回值后只做一件事：决定播哪个动画。

```python
path = self.path_cells(piece)
blocker = self.find_blocker(piece)

if blocker is None:                        # 前方无阻挡 -> 整条箭头飞出
    for r, c in piece.cells:
        self.grid[r][c] = None
    self.remaining -= 1
    if self.remaining == 0:
        self.state = STATE_CLEARED
    return ClickResult(CLICK_FLY, piece, None, path)

self.hp -= 1                               # 前方有阻挡 -> 丢一颗心
if self.hp <= 0:
    self.state = STATE_FAILED
return ClickResult(CLICK_BLOCKED, piece, blocker, path)
```

注意飞出时要清的是 `piece.cells` **全部格子**，不是一格——一个「点中一格消掉一整条」的
操作就这么来的。这样测试可以完全绕过渲染直接验证规则，动画也永远不会反过来改状态。

### 3.5 飞出与撞击的表现

* **飞出**：`FlyOut` 让整条箭头**沿自己的折线路径滑出去**，像贪吃蛇转弯的连续版——
  箭头先钻出去，拐弯顺着身体一路「流」到尾巴，全程连续插值、不是一格一格地跳。
  实现上是把各格中心连成折线（过箭头后沿箭头方向直线延长），每个折点沿路径
  前进相同的弧长 `advance`，每帧按新折点直接画两遍（描边 + 本色），
  不再走整张贴图的缓存——贴图是刚体，表达不了「弯折在移动」。
  `advance` 用 `progress ** 1.7` 做缓入，看起来像被抽出去一样越来越快；
  总弧长按「尾到箭头的弧长 + 箭头到视口出口的距离 + 0.9 个格子」算，保证彻底离场。
* **撞击**：`Impact` 动画做三件事——沿方向前冲 18% 格宽再弹回（`sin` 曲线）、
  垂直于前进方向做衰减抖动、箭头泛红并向外扩散一圈红框。
  整个动画 0.36 秒，结束后自动从动画列表移除。
* **丢心**：`FloatingHeart` 把像素心复制成左右两半，每帧分开旋转、边倾斜边淡出往上飘，
  前 30% 时间保持不透明，避免玩家还没看清就消失。

### 3.6 生命值、得分与关卡难度

这一块是后期迭代出来的，我觉得是这次最有意思的部分。

**先定义「难」**。这个玩法有个容易被忽略的性质：点掉一支能飞出去的箭头，
只会让其它箭头的射线更空，所以**任何一步正确操作都不会把自己玩死**——
它不存在「顺序错误」，唯一会输的方式是点了一支其实被挡住的箭头。
于是难度**只来自一件事：在棋盘上找出此刻哪些箭头的箭头前方是空的**。

**难度分**因此定为：

```
难度分 = 箭头数 × 1.6 + 棋盘格数 × 0.12 − 开局可点数 × 3.0      → 再映射成 1~5 颗星
```

刻意**不含生命值**：生命值是按关卡序号直接给的（见下），要是再把生命值算进难度分，
就成了「难度高 → 给的心多 → 难度算下来变低 → 星级跳回去」的循环。

**生命值按关卡序号给**：第 1~4 关 3 颗心、第 5~9 关 4 颗心。前期棋盘小、
要扫的射线少，3 颗足够；后期棋盘大、步步都要算，多给一颗。
最初一版是按难度星级给 4~7 颗，实测太宽松——后期丢两三颗心根本不疼，
改成 3/4 颗之后每一次点错都要掂量一下。

**得分按剩余生命值的比例折算**，而不是「每错一次扣固定分」：

```
基础分   = 星级 × 250
本关得分 = 基础分 × 剩余生命值 ÷ 生命值上限
完美奖励 = 一颗心都没丢时，再额外 +20% 基础分
```

为什么按比例：各关生命值上限不一样，固定扣分会让心多的关卡显得无所谓
（4 颗心的关卡丢 1 颗还剩 3 颗，扣的却和 3 颗心的关卡一样多）。
按比例折算则始终是「这一颗心占本关全部容错的多大一份」，和玩家直觉一致。
于是每关满分正好是「星级 × 300」。

### 3.7 教学关、关卡总览与进度存档

**教学关**的引导要能**自愈**：玩家完全可以不按提示点。所以每一步在展示前都会和棋盘状态
对一次账——目标格子已经飞走了、或者这一步的前提（比如「它被挡住了」）已经不成立，
就自动跳到下一步，绝不会出现「让你去点一支已经不在棋盘上的箭头」这种尴尬。
实现在 `Game.sync_tutorial()`。

教学关**不放进 `LEVELS`**，而是单独的 `TUTORIAL` 常量：它不计分、不占关卡编号、
不需要解锁，主菜单上有独立入口。这样编号就从第 1 关「初次拉弓」干净地开始，
玩家也不会把教学关误当成一道要拿分、要解锁的题。

**进度存档**用 JSON 而不是 `pickle`（原因见第四节记录 6）：

```json
{ "version": 2, "cleared": [0, 1, 2], "scores": { "0": 300, "1": 300 } }
```

解锁规则只认**从头连续通关的前缀**，实现就是在第一个没通关的关卡处 `break`——
跳着通关不算数，难度递进不会被绕开。存档升级到 version 2 加了 `scores` 字段，
读的时候用 `data.get("scores", {})`，老存档读进来就是「都没得分」，不会因为升级而丢进度。

### 记录 1：第 2 关摆出了死局

**我的要求**：设计 4 个难度递进的关卡，用文本布局表示，第 2 关要「有且只有一支箭能直接飞出去」，
用来教玩家「先找出口」。

**AI 提供**：直接给了 4 关布局。第 2 关长这样：

```
.....          (1,1) 的「>」被 (1,3) 的「v」挡住
.>.v.          (1,3) 的「v」被 (3,3) 的「<」挡住
.....          (3,3) 的「<」被 (3,1) 的「^」挡住
.^.<.          (3,1) 的「^」被 (1,1) 的「>」挡住
.....
```

**实际效果**：开局可点的棋盘数量是 **0**。四支箭头首尾相接围成一个环，互相指责，
谁都飞不出去——这一关是**无解**的。

**我的处理**：其实我当时也没一眼看出来，是写完校验脚本后报的警。顺着「谁挡住了谁」
捋一遍就明白了。修改办法很简单：把 `(3,3)` 的 `<` 挪到 `(3,4)`，
它左边依然是 `(3,1)` 的 `^`（保持阻挡关系不变），但不再挡在 `(1,3)` 的 `v` 下方了。

**这件事的价值**：它让我意识到**关卡不能靠眼睛验收**。后来我把「所有关卡必须可解」
直接写成了单元测试，布局一改就会被自动拦住。
（这一版关卡重做成弯曲箭头之后，第 2 关已经换成了 13×9 的新布局，
但这条教训留到了今天：`validate_layout` 在导入时就拦非法形状，校验脚本与单测再各解一遍。）

### 记录 2：为什么用贪心判断关卡有解

**我的要求**：写一个脚本，能自动判断关卡能不能通关，并给出一个参考通关顺序。

**AI 提供**：反复扫描棋盘，把当前能飞出的箭头全部消掉，直到不能再消；还有剩余就说明无解。

**实际效果**：跑起来完全正确。但我不太放心——「每次都消所有能消的」这种贪心，
会不会因为选择顺序不合适而漏掉真正的解？

**我的处理**：我补了一个证明，并把它写进了代码注释：

> 消除一支箭头只会让其它箭头的射线**变得更空**，永远不会让某条射线变得更堵。
> 也就是说「某支此刻能飞」这个性质具有**单调性**：此刻能飞，之后任何时刻都还能飞。
> 既然不会因为选择而失去任何机会，那么反复「消掉当前所有能飞的」就是完备的——
> 能全消掉就一定有通关顺序，卡住了就说明真的无解。

这条单调性还写成了测试（`test_solver_is_monotonic`）。另外我专门构造了一个**必然死锁**的
布局做反向验证，这个用例跑通之后我才确信校验脚本可信。

### 记录 4：测试用例首轮 4 个失败

> 用例扩到了 **222 个**，最终结果见第六节。

两次都不是改游戏，而是改测试——但**前提是你得先看懂源码到底怎么运行的**，
这也正好说明「AI 生成的代码必须自己理解」不是一句空话。

### 记录 5：让 AI 生成关卡，结果它挑出来的全是最简单的

**我的要求**：再加几关，难度要递增，而且每一关都必须能通关。
随机撒很容易撒出无解布局，所以我要求 AI 写一个生成器，用已有的求解器当验收。

**AI 提供**：`tools/generate_levels.py`，思路是「随机撒 → 用贪心求解器筛掉无解的 →
按难度分排序取前几名」。

**实际效果**：筛出来的关卡确实都能通关，但**全部是开局几乎每支都能飞出去的松布局**。
10×10 摆 30 支，开局可点 24 支——玩家随便点都能过，难度根本谈不上。
翻代码才发现，排序那行方向写反了：难度分里「开局可飞行数」是负权重，
我却按升序取前几名，等于专门挑最简单的。

**我的处理**：先停下来想清楚一件事——**这个游戏到底难在哪里**（就是 3.6 节那段推理）。
想通之后，生成器换成两条新做法：

* **逆向构造**：把「消除顺序」倒过来当「放置顺序」，放置时只要求「新箭头箭头正前方
  没有已放置的箭头」，这样放置顺序的逆序天然就是一个合法通关顺序，布局**必然可解**，
  连事后筛选都不需要；
* **阻挡偏好**：维护一张 `seen` 表，记录每个格子「被多少支已放置箭头的射线覆盖」，
  放置新箭头时优先选这些格子——新箭头正好落在老箭头前方，老箭头就得等它先走。
  这张表让判断「这格会不会挡住别人」变成 O(1)，不然每放一支都要重扫全盘。

结果：同样是 10×10 / 30 支，开局可点数从 24 支压到 **7 支**，玩起来才真的需要一行一行地扫。

**这件事的价值**：排序方向写反是个很低级的错误，但更值得注意的是——
**AI 不会觉得「挑出来的关太简单」有什么不对**，因为它没有「这一关玩起来应该是什么感觉」的直觉。
「什么叫做难」这件事必须由人先定义清楚，再翻译成能写进代码的指标。

### 记录 6：进度用 pickle 存，看着能用其实是个雷

**我的要求**：记录玩家已经通关到第几关，没通关前面就不让玩后面；关掉游戏再打开，进度还在。

**AI 提供**：把已通关关卡的下标集合 `pickle` 到一个文件里，启动时 `pickle.load` 读回来。

**实际效果**：能跑。但有两个问题一看就心里发毛：

1. `pickle` 是二进制，存档出问题时**打不开也看不懂**；
2. 只要文件损坏（比如写到一半断电），`pickle.load` 会直接抛异常，
   **整个游戏在启动时就崩掉**——对一个要交给老师演示的作业来说这是致命的。

**我的处理**：

* 换成 JSON：存档打开就是 `{"version": 2, "cleared": [0, 1, 2], "scores": {...}}`，一眼能看懂；
* 加容错：读失败当作空进度，写失败只在控制台警告一次，游戏照常能玩。
  这是一个有取舍的决定——严格报错更「正确」，但演示场景下「能继续玩」更重要；
* 把解锁规则从界面代码里抽出来，放到不依赖 pygame 的 `progress.py`，
  于是「通关一关才解锁下一关」这条规则可以用普通单测覆盖，不必为了测一条 `if` 去创建窗口。

**这件事的价值**：AI 给出的方案经常是「功能可用」就停了，**异常路径完全是空白**。
凡是会落盘的东西，都要自己问一句：文件损坏了会怎么样？目录没写权限会怎么样？

### 记录 7：「塞得越多越难」，实测正好相反

**我的要求**：后面几关再难一点。

**AI 提供**：很自然的建议——把棋盘放大，再往里多塞，密度上去难度就上去。

**实际效果**：放大棋盘确实有用，但**提高密度完全没用，甚至反着来**。
实测数据很反直觉：

| 棋盘 | 箭头数 | 占格率 | 开局可点数 |
| --- | --- | --- | --- |
| 9×9 | 30 支 | 0.37 | 7 支 |
| 9×9 | 54 支 | 0.67 | **18 支** |

塞进去的箭头多了将近一倍，开局能直接点的反而从 7 支涨到 18 支，比稀疏时还简单。

**原因是我想了一会儿才想明白的**：**贴着棋盘边缘、朝着棋盘外的箭头，它的射线长度是 0，
永远能飞**。密度一高，剩下的合法放置位置几乎只剩这一类（它们永远合法），
于是整个布局退化成「一大半开局就能点」的松局面。

**我的处理**：给生成器补两条：

1. **排除空射线候选**：除最后一步外，一律避开射线为空的候选位置；
2. **打分里加上「自己射线的长度」**：只优化「能挡住别人」而不优化「能被别人挡住」是不够的。

**这件事的价值**：AI 给的方案在**逻辑上**都没错——多放确实会让棋盘更挤。
错的是它没有「玩起来是什么感觉」这一层判断，而这层判断只能靠自己跑一遍数据才能发现。
**能算的就要算，不要凭感觉。**

**这件事的价值**：用户说「不好看」时，别直接开始调色——先把这句话变成一个**可测量的数字**
（相邻同色对占比、亮度跨度），改完再拿同一个数字验证，否则只是在凭感觉换配色。
另外也说明**用户两次看似矛盾的要求（先「太单调」后「要统一」）其实说的不是一回事**：
前者指同类元素连成一整块，后者指同类元素之间深浅不一，两边都要满足。

**我的要求**：找了一张同类游戏的截图当参考，让 AI 把界面改成那个样子——
纯色背景、棋盘只留点阵（不要卡片格子）、棋子做成**糖果色的胖管子**、
顶部居中一条信息栏（关卡名 / 计时 / 生命值 / 剩余箭头数 / 得分）、底部一排工具按钮。

**AI 提供**：一次给全了配色常量、箭头绘制函数、图标集和整块 HUD 布局。
第一版跑起来大方向是对的，但截图逐张看下来，还是有三处不对味：

### 记录 11：把「一格一支箭头」改成「占多格的弯曲箭头」

**我的要求**：参照画面里根本不是「一格一个箭头」，而是一条**蜿蜒的箭头**，

**AI 提供**：箭头模型的初稿——把棋子从「一个坐标 + 方向」换成「一串相邻坐标 + 一个方向」，
渲染时沿着这串坐标画一条圆角粗线，末端补一个三角。

* 旧的规则代码到处在读 `board.arrows`、`arrow.row`、`arrow.col`、`arrow.delta`，

* 关卡数据全部重写成箭头写法，并用生成器重新出一遍题；
* 工具脚本按新 API 重写，测试按新 API 重写（这一步的工作量最大）。

**这件事的价值**：**「换个表示法」从来不只是换个数据结构。**
AI 改得很听话——你让它把箭头画成管子，它就把箭头画成管子；
但「所有依赖旧表示法的代码都会失效」这件事它不会主动告诉你。
真正的工作量在**连锁影响**上，而判断连锁影响的范围是人的活儿。
这也是为什么我坚持「规则模块不许 import pygame」：
正因为它不碰界面，这次重做时我才能确定**只改数据的表示、不改规则的正确性**。

### 记录 12：辅助线斜穿整个棋盘

**背景**：加完「辅助线」功能之后，截图逐张检查时发现有几条线明显不对——
它们斜着穿过整个棋盘，连到一个跟箭头方向完全无关的格子上。

**原因**：画线的时候要决定「线画到哪为止」。AI 写的代码是这样的：

```python
path, blocker = self.board.path_to_blocker(piece)
if blocker is not None:
    return start, self.cell_center(*blocker.head)     # BUG
```

`blocker.head` 是**挡路那支箭头的箭头**。上一版棋子只有一格，箭头就在那一格，
所以这个写法是对的；改了箭头模型之后，一支占好几格，**压在射线上的通常是它的身子**，
它的箭头可能在很远的另一头——于是线就从箭头方向斜着连过去了。
更糟的是，如果那支箭头的箭头恰好不在射线上，`path.index(blocker.head)` 会直接抛
`ValueError`，悬停到这类箭头上游戏就崩。

**我的处理**：改成用「**射线上被占的那一格**」，也就是 `path_to_blocker` 返回的路径最后一项：

```python
def guide_segment(self, piece):
    """这条辅助线的两个端点；箭头已经飞走时返回 None。"""
    ...
    path, blocker = self.board.path_to_blocker(piece)
    if blocker is not None:
        return start, self.cell_center(*path[-1])      # 射线上被占的那一格
    return start, {方向: 棋盘边}[piece.direction]
```

顺手把它抽成一个独立方法 `Game.guide_segment()`，并补了 3 条几何测试：

* `test_guide_segment_is_parallel_to_the_arrow`——用**叉积为 0** 卡「必须和箭头共线」，
  用点积卡「长度和射线一致」；
* `test_guide_segment_ends_inside_the_blocking_cell`——被挡时终点必须落在那一格的矩形里；
* `test_guide_segment_disappears_with_the_piece`——箭头飞走之后线也要消失。

> 写这几条测试时还踩了一次浮点：朝棋盘外、射线长度为 0 的箭头，理论上线长应该是 0，
> 但两个端点各自取整之后算出 `-0.5`，被 `assertGreater(length, 0)` 拦下来了。
> 改成「射线为空时断言 `abs(length) <= 1`（给个浮点余量），非空时才要求严格大于 0」。

**这件事的价值**：这个 bug **不是靠读代码发现的，是靠看图发现的**——
测试全绿、逻辑「看着对」，只有把它画出来才知道线歪了。
而它的根因是**同一个概念在上下文变了之后变味了**：
`blocker.head` 在「一格一支」的世界里等于「挡路的那一格」，在箭头世界里不再等于。
把这种判断从界面搬到棋盘层、再抽成一个有名字的方法、最后用几何量卡住，
才算真的修好了而不是绕着它走。

### 记录 13：演示 GIF 有 8 MB

**背景**：录完演示动画，文件有 8000 KB，网页上加载要等很久，明显不正常。

**原因**：我在拼帧的时候给每帧加了 `disposal=2`（每帧先把整块画布清成背景再画）。
本意是「免得上一帧残影留下」，但 Pillow 的行为是：一旦发现帧不是完全透明，
就**放弃帧间差分、每帧整幅写一遍**。2400×576 的整幅编码写了 184 次，体积自然爆炸。

**我的处理**：

* **去掉 `disposal=2`**，让 Pillow 走默认的 `disposal=0`（帧间差分），只写变化的像素块；
* 等比缩到 0.6 倍（当时的窗口是 600×960，即 360×576；后来窗口改成 680×880，现在是 408×528）；
* 调色板降到 128 色；
* 中段用「快进录」：按住解法把几步一条过，只录关键的那几个转折。

改完体积从 8000 KB 降到 **2300 KB**，画质肉眼看不出差别
（关卡与箭头改版后重录为 2419 KB / 199 帧）。
> 顺带记一笔：这条路子后来又被**背景动效**顶回来一次——
> 帧间差分的前提是「大部分区域不动」，背景一活就不成立了，
> 体积从 2.6 MB 涨到 4.2 MB，只能把抓帧率降到 10fps（见记录 21）。

**这件事的价值**：GIF 体积不是「压一压」就行的，得先搞清**编码器到底在做什么**。
我一开始也想当然地以为「加 disposal 是清理，清了更干净」，
实际读了 Pillow 的 `GifImagePlugin` 源码才明白它把帧间优化给关掉了。
**猜优化的方向，往往正好猜反。**

### 记录 14：飞出动画从「整条平移」改成「沿路径滑出」

**背景**：箭头版做完后自己试玩，总觉得飞出的那一瞬间不对劲——
箭头是一张刚体贴图，朝箭头方向整体平移，拐弯的部分是**横着蹭**出去的，
不像「钻出去」，更像「被拖走」。

**我的要求**：飞出的时候像贪吃蛇转弯那样，箭头先钻出去，拐弯顺着身体传到尾巴；
但不要一格一格地跳，要顺滑。

**AI 的方案**：把各格中心连成折线，过箭头后沿箭头方向直线延长；
飞出时**每个折点沿路径前进相同的弧长**，每帧按新折点位置直接重画箭头。
因为每点走的弧长一样，弯折会连续地「流」过去——这正是贪吃蛇转弯的连续版。
缓入沿用 `progress ** 1.7`，加速感还在。

**踩的坑**：

* 原来的飞出画的是**整张贴图**（缓存好的 Surface），刚体表达不了「弯折在移动」，
  所以动画那不到半秒必须绕开缓存直接画——描边、本色两遍照旧，观感才和静止时一致；
* 总滑行弧长不能照搬旧算法：旧的是「最靠后的边到视口出口」的直线距离，
  新的要加上「尾巴到箭头的弧长」，不然长箭头滑不完就停在中途；
* 弧长落点的边界（正好等于折线总长时）先写了 `<=`，数组越界，测试当场抓住。

**验证**：L 形箭头在半格、一格半、两格、两格加 25 像素四个时刻，
尾巴的位置必须正好落在原始路径的对应点上（`test_fly_out_tail_follows_the_bend`），
再加无头渲染中间帧肉眼确认弯折确实在流。

**这件事的价值**：表现层的改动也可能牵动几何，**「顺滑」两个字背后是弧长参数化**——
把动画量从「位移向量」换成「沿路径的弧长」，贪吃蛇的效果就自然出来了。

### 记录 15：关卡里全是等长箭头，长短差距拉不开

**背景**：飞出动画改完再看盘面，发现另一个观感问题——
每关的箭头几乎都一样长（第 1 关一水儿的 5 格、第 9 关一水儿的 10 格），
整盘看起来像尺子铺出来的，没有节奏。

**我的要求**：长短差距拉开一点，一盘里既有两三格的短箭、也得有几支特别长的。

**AI 的方案**：先找原因——生成器给每支箭打分时「占的格子越多越好」，
于是每支都朝长度上限长满。改成**开工前先抽签**：以「平均单支长度」为中心、
大方差正态地抽一个目标长度，打分从「越长越好」改成「离目标越近越好」；
长短差（长度标准差）同时写进选关器的排序键，铺满率不够 0.91 的直接淘汰。

**踩的坑**：

* 目标长度允许抽到 1 格时，大盘的铺满率从 0.93 掉到 0.79——
  1 格箭在半满的盘上最容易把周围射线截成死角，后面没有位置能再放新箭；
  下限卡到 2 格后恢复；
* 铺满率和长短差天然打架：长短差越大、死角越多。最后靠分工解决——
  **硬门槛保铺满率（0.91），排序键保长短差**，两者各管各的。

**验证**：第 9 关重挑后箭长 1~18 格（标准差 4.6），铺满率 0.94；
222 条测试与关卡校验全部重跑通过，九关的长短差、朝向分布、星级与总分 7500 都已对齐。

**这件事的价值**：观感问题也要先翻译成**可量化的指标**才能改——
「长短不齐」变成「长度标准差」之后，它才能进打分、进排序、进门槛，
而不是每次靠肉眼盯着调。

### 记录 16：箭头朝向一边倒，四个方向挤成两个

**背景**：长短差解决后又对照参考图看盘面，发现更扎眼的问题——
箭头**朝向**太规律：第 1 关 76% 朝下、第 4 关只有「上/右」两个方向、
第 7 关 74% 朝下。参考画面里箭头是上下左右均匀混着指的。

**我的要求**：朝向别再一边倒；前期关卡的箭头也再细一点；
生命值改成第 1~4 关 3 颗、第 5~9 关 4 颗。

**AI 的方案**：还是先量化——「最大单朝向占比」。根因在生成器的打分：
「射线越长加分越多」让箭头集体朝棋盘长边指。给生成器加**朝向均衡罚分**
（同方向比当前最少的方向多几支就罚几分，罚的是差值而不是绝对数，
保证永远有一个零罚分方向），再把占比写进选关器的排序键。

**踩的坑**（这次坑特别多）：

* 罚分太弱压不住：线性罚到 12 也只能把最差占比从 76% 压到 69%——
  盘面过半后大多数空位只剩一个通射线方向，**没得选**；
* 改成「按配额强制方向」更糟：被限方向放不下就回退全方向，
  回退候选反而高分胜出，最差占比冲到 89%；
* 让选关器偏向均衡后第一轮跑出「最大单朝向 100%」——
  排序元组按**大者胜**比较，「越小越好」的指标忘了取负号，
  修完又把「达标=0 / 兜底=1」写反了一次，前功尽弃；
* 均衡和「开局可点数压到 2~3」天然打架：四向摊开的箭有更多朝外的，
  出口天然变多。大盘试了「堵箭奖励」「超强朝内偏好」都不划算，
  最后接受现实——**后期目标可点数放宽到 4~6，用 3/4 颗心的紧生命值补难度**。

**验证**：九关重新生成后最大单朝向占比 26%~45%（此前最差 76%），
四个方向全部出现；箭头线宽在 56px 格距下从 22px 收到 17px
（大格距按幂函数收细，小格距不动）；生命值换成 `HP_BY_LEVEL` 表；
222 条测试与关卡校验全部通过。

**这件事的价值**：一是「罚相对差值」比「罚绝对数」聪明——基准跟着盘面走，
罚分差不会被稀释；二是排序键里混着「越大越好」和「越小越好」的指标时，
**负号是最容易翻车的地方**，同一个坑一晚上摔了两次。

### 记录 17：电脑上窗口装不下，飞出动效也不够丝滑

**背景**：实机试玩发现两个问题。一是 600×960 的竖屏窗口在电脑上超出了
屏幕可视范围，底部的按钮和工具栏被任务栏挡住；二是飞出动画改到
「沿路径滑出」之后，动效还是不够顺——起步黏、飞快时边缘有锯齿。

**我的要求**：窗口改宽一点或改矮一点，电脑上能看到全貌；飞出动效再丝滑一点。

**AI 的方案**：两个问题分开治——

* **窗口**：逻辑分辨率从 600×960 改成 680×880（又宽又矮）。这还不够保险：
  屏幕如果开了 125% / 150% 缩放，880 也装不下。所以 `main.py` 再加一道
  自适应——启动时量一下桌面尺寸，装不下就开一个等比缩小的窗口，
  整幅逻辑画面每帧 `smoothscale` 缩进去（带抗锯齿），鼠标坐标按比例

  它们永远只认 680×880 这一套坐标；
* **动效**：不丝滑的来源拆成两半。一半是**缓动曲线**：原来的 `t^1.7`
  前 0.1 秒几乎不动、然后突然窜出去，手感是「卡一下再飞」；
  幂次降到 1.35（提成了 `config.FLY_EASE_POWER`），起步立刻有位移、

  smoothscale 回来，相当于 2×SSAA，运动边缘顺滑得多。
  画布先和视口裁剪框求交，飞出视口的部分不画，实测单帧只多花
  0.2 毫秒左右。

**验证**：222 条测试全部通过；16 张截图与演示 GIF（408×528、2625 KB）
按新窗口重录；动画绘制耗时 60 帧均值 0.19ms，60 FPS 无压力。

**这件事的价值**：**「界面代码只认一套逻辑坐标」这条纪律又救了一次**——
正因为所有尺寸都从 config 常量推导，窗口适配只改了入口一个文件；
要是布局里散落着写死的 600×960，这就是一次全项目的地毯式返工。

### 记录 18：想要 C 形 / S 形箭头，飞出要像绳子一样顺

**背景**：九关重生成后盘面好看了，但形状全是「直条 + 一两个直角拐」；
而且箭头是直角折线画的，拐角生硬，飞出时也硬邦邦。

**我的要求**：有的箭头可以弯成 C 形或者 S 形，提高难度的同时丰富形状；
箭头飞出去的时候，整条要像**绳子**一样丝滑。

**AI 的方案**：两件事分开做——

* **绳子渲染**：把「直角折线」升级成「圆角曲线」——每个拐角附近取一段，
  用二次贝塞尔把直角削成圆弧，再沿采样点画圆头粗线。静态棋子、飞出动画
  共用这一条曲线，拐弯处再也不会有棱角；
* **C/S 形生成**：给生成器的「往回长」过程加形状加权——C 形要求下一个弯
  和上一个**同号**（一直往同一边卷），S 形要求**交替**（蛇形蜿蜒）；
  选关器按关卡配掺入比例，教学关之外从第 4 关开始认识 C 形；
* **飞出时长随路径伸缩**：长蛇形箭的滑行弧长是短箭的好几倍，
  还用同一个时长就会「瞬移」——改成按格距速度换算时长，夹在上下限里。

**踩的坑**：

* 最有意思的一个：最初怎么都弯不出 C 形。原因是步进模型里只允许
  「沿箭轴 / 垂直方向」两种移动，从垂线拐回箭轴的叉积符号**必然**和
  上一个弯相反——C 形在这个模型里**结构上不可能出现**。
  把「沿箭头方向」也加进可走选项后才卷得出来；
* 顺手把「直行」判定改成按当前朝向，结果所有箭（包括不掺蛇形的）
  都变得弯弯绕绕，26×18 大盘铺满率直接崩掉——直行高权重是铺满率的命根子，
  回退；
* 大盘掺蛇形的比例有天花板：0.22 时 24 个种子全军覆没（S 形占格多、难塞缝），
  最终策略是「少量定向补 C 形，S 形交给长箭自然弯折」。

**验证**：`rope_points` 曲线首尾不动、拐角被削圆（新增 6 条用例）；
高掺入率下蛇形布局仍然合法可解；231 条测试与关卡校验全部通过。

**这件事的价值**：**「形状是否可能出现」要先看生成模型的结构**——
C 形不是概率调出来的，是模型里根本没有那条通路；而渲染层把「折线」
抽象成「采样点列」之后，绳子感和飞出动画是同一个抽象的白送成果。

  采样面板底色，盯住「卡片别爬回来」；一条守住「标题 → 副标题 → 进度 → 按钮」

**验证**：230 条测试通过；无头渲染两种进度状态截图核对排版。

**这件事的价值**：**界面上每多一块说明，主按钮就少一分存在感**。
规则和教学关的五个步骤本来就是同一份内容，放在两个地方不但冗余，
还让第一眼看到的东西从「开始游戏」变成了「一大段字」。
删掉之后什么都没少——想学规则，点教学关；想玩，点主按钮。

### 记录 21：背景来点动图

**背景**：前几轮一直在做减法——界面清爽了，底子也「干净」了。
代价是画面太静：早年为对齐参考图，把星点和流星都改成了「相当于不出现」
（`BG_STAR_COUNT = 0`、流星间隔 999 秒），只剩两团几乎看不出在动的光晕。
静态截图看着没毛病，真机跑起来就是一潭死水。

**我的要求**：背景来点动图。

**AI 的方案**：在「不抢戏」的前提下把动效加回来，一共四层，
全部走**预渲染贴图 + 每帧只 blit**，逐像素运算一个都不做：

* **极光带**（新的主角）：几条斜向柔光带缓缓往下流过。做法是把一团圆形柔光
  横向拉成椭圆、再逐列错位做出倾角，滑出下边就从上面重新下来；
* **漂移光晕**：原来的两团保留，行程和亮度都放开了些；
* **浮尘**：把早年的星点改活了——上浮更慢、亮度压到原来的一半、
  加了左右钟摆和更长的闪烁周期，数量也从「一屏星海」收到 30 个；
* **流星**：间隔从 999 秒调回 12~26 秒。
* **浓淡分场景**：`set_scene()` 里游戏界面拿菜单的 45%，
  浮尘 30 → 14，流星间隔拉长一倍——棋盘上要判断的事已经够多了。

**踩的坑**（这一轮四个坑里三个是「看图才发现」的）：

* **日间主题变成脏玻璃**：日间是浅底，加法光会糊成白斑，所以改成**减法**叠加做「云影」。
  结果第一版直接沿用夜间那套发光色去减，画面出现满屏红绿黄条纹——
  浅蓝底减掉「偏蓝的光」等于给底子**上了补色**，青带被减成暗红、紫带被减成绿色。
  换成三通道接近的中性灰蓝之后才是干净的云影；
* **光带的端头露在画面里**：光带是一条**有端头的椭圆**，宽度不够时
  端头就落在屏幕内，看着像渲染出了 bug——一个好端端的柔光带被切了个圆钝的截口。
  两处一起收：宽度盖满整屏还有富余、横向摆动的幅度比「多出来的那截」更小；
* **倾斜的性价比**：光带又宽又扁（一屏多宽、百来像素高），
  用 `pygame.transform.rotate` 倾斜是按**外接矩形**收费的——13° 就能把
  1360×110 撑成 1340×480，十几张贴图白吃 21 MB 内存。
  改成逐列错位之后同样的观感只要 **8.1 MB**。这里还顺手错了一次方向：
  第一版按**行**错位，带子的端头斜了、带子本身还是水平的，等于没生效；
* **GIF 一夜之间胖了 60%**：演示 GIF 的体积一直靠 Pillow 的**帧间差分**撑着
  （最早是 `disposal=2` 让差分失效，8 MB；去掉之后 2.6 MB）。
  背景一动画，这条前提就没了：**差分是按矩形算的，一像素的涟漪和十像素的位移都要写满全屏**。
  12fps 直接冲到 4.2 MB，抓帧率降到 10fps 才落回 3.7 MB。

**验证**：新增 10 条背景用例（光带下沉会绕回、端头不落在画面里、亮度分档缓存不涨、
`_tilt` 只加高度不加宽度、浮尘上浮回绕、流星按计时出现又收掉、游戏界面比菜单收敛、
日间改做云影、数量写 0 真的关掉、日间只画不炸），共 **240 条测试全部通过**；
无头实测单帧 **1.5 ms**（菜单 1.67 ms / 游戏 1.42 ms），贴图缓存 8.1 MB；
16 张截图与演示 GIF 全部重录。

**这件事的价值**：**「动起来」的代价不在位移，而在「每帧都在变」这件事本身**。
一个几乎看不出在动的光晕，对缓存策略和 GIF 压缩的破坏力跟全屏闪烁是一样的——
它逼着所有下游都放弃「大部分区域不变」这个假设：
贴图缓存得按亮度分档，否则呼吸动画每帧都在生成新贴图；
GIF 得降帧率，因为差分再也压不出体积。
反过来也成立：**只要一开始就假设「每帧都在变」，这两件事反而都能便宜地做掉**。

**满分合计 8100 分**（9 关合计 281 支箭头，单支最短 1 格、最长 18 格）。

难度曲线的做法是**先量、再插**。九个关卡的难度分是
`27.6 / 32.8 / 37.0 / 52.3 / 55.7 / 77.8 / 85.4 / 103.7 / 114.8`，
一路单调递增。三条性质都写成了断言：棋盘只许变大、箭头只许多、
星级不下降；开局可点数不设硬目标（能完成就好），只卡
「第 1 关好找、任何一关不满盘乱点」的区间，另有下限防止难度反超下一关。

**难度轴这一版换过一次，理由值得记一笔。**

上一版是「棋盘冻结在 9×9，之后靠提高密度加难」。
这一版重做成箭头之后，这条轴**不成立了**，因为：

* 一支箭头占 4~9 格，密度不可能像单格棋子那样往上堆；
* 真正变难的原因变成了「**要扫的射线变长变多**」——棋盘越大、箭头越长、交叉越多，
  一眼能扫完的部分就越少。

所以现在的做法是：棋盘从 11×8 一路放大到 26×18，箭头从 20 支加到 46 支，
单支长短从 1 格散开到 18 格，后期还掺了**蛇形箭**（C 形回折、S 形蜿蜒），
而开局可点数不设硬指标、九关实测都落在 4~6 支
（由 3/4 颗心的紧生命值补难度）。它依然是真正决定手感的那一项。

| 进度 | 通一关后总览里那张卡片立刻变绿并解锁下一张；关掉再开，进度和最高分都在 |

## 七、遇到的问题汇总

| 问题 | 现象 | 原因 | 解决方式 |
| --- | --- | --- | --- |
| 第 2 关无解 | 校验脚本报 `可解=False`，开局可点为 0 | 四支首尾相接形成死环 | 挪走一支，重新校验；并把「关卡必须可解」写成单测 |
| 中文字体加载崩溃 | `TypeError: ... not int` | pygame 枚举 Windows 注册表字体时崩溃 | 改为按路径直接加载 `msyh.ttc` 等字体文件 |
| 测试首轮 4 个失败 | 断言数值对不上 / 点击不扣生命值 | 测试关卡数量写错；辅助函数把已飞出的当成被挡的 | 按实际布局修正数值；辅助函数加「仍在棋盘上」的过滤 |
| 悬停高亮了不该高亮的格子 | 挡路箭头之后的路段也被点亮 | 高亮用了完整路径，没在阻挡处截断 | 把路径截断到被占的那一格为止 |
| 动画还没播完就弹出结果面板 | 最后一支还在飞，通关面板已经盖上来 | 状态切换和动画没有解耦 | 通关 / 失败后延迟 0.70 秒再弹面板 |
| 生成的关卡全是简单关 | 10×10 摆 30 支，开局可点 24 支 | 难度分排序方向写反，等于专挑最简单的 | 改成降序，并换成「逆向构造 + 阻挡偏好」 |
| 提高密度反而更简单 | 9×9 塞 54 支时开局可点 18 支（塞 30 支时只有 7 支） | 贴边、朝棋盘外的箭头射线为 0，永远能飞 | 生成器排除空射线候选，并给「自己射线长度」加权 |
| 配色忽明忽暗 | 同一方向的箭头深浅不一，看着杂乱 | 用固定坐标取 4 档明暗变体，感知亮度差到三倍 | 去掉变体、一方向一色，用加权公式把四色亮度拉平并写成断言 |
| 同色箭头糊成一片 | 一整排同色箭头贴在一起，看不出是几支 | 颜色随机分配，没有相邻约束 | 改成 12 色糖果 + 贪心染色，`test_no_two_adjacent_pieces_share_a_color_in_any_level` 逐关卡住 |
| 朝下的箭头全部解析失败 | 关卡导入直接报「写法不合法」 | 对整串调了 `upper()`，`v` 变成 `V` 查不到表 | 只大写路径段，方向字符按小写查表；补一条用例 |
| 改箭头模型后全线报错 | `AttributeError: 'Board' object has no attribute 'arrows'` | 「一格一支」的表示法换了，所有依赖它的代码都失效 | 新建 `pieces.py` 收拢几何；规则改按格子归属判断；关卡与工具链重写 |
| 100% 缩放时棋盘溢出视口 | 最下面一行被工具栏切掉 | 格子边长按浮点算之后整体超出了视口高度 | 边长向下取整，并对平移量做夹取；补「棋盘不溢出」用例 |
| 辅助线斜穿整个棋盘 | 线连到一个与箭头方向无关的格子；悬停时还抛 `ValueError` | 用 `blocker.head`（挡路那支的**箭头**）当终点，而它未必在射线上 | 改用「射线上被占的那一格」，抽成 `guide_segment()` 并补 3 条几何测试 |
| 演示 GIF 有 8 MB | 网页加载要等很久 | 给每帧加了 `disposal=2`，Pillow 因此放弃帧间差分、每帧整幅写 | 去掉 `disposal=2`，缩到 408×528、降到 128 色，体积回到 2.6 MB 上下 |
| 背景一动，GIF 又胖了 60% | 2.6 MB → 4.2 MB | 帧间差分的前提是「大部分区域不动」，而极光带 / 浮尘 / 光晕**每帧都在变**，差分要写满全屏 | 抓帧率 12 → 10（落回 3.7 MB）；真想要 2 MB 出头，录制前把 `BG_AURORA_COUNT` / `BG_STAR_COUNT` 写 0 |
| 日间主题出现满屏红绿条纹 | 一条条暗红、暗绿的色带，像蒙了脏玻璃 | 用夜间的发光色做**减法**：浅蓝底减掉「偏蓝的光」等于给底子上**补色**（青带变红棕、紫带变绿） | 日间换三通道接近的中性灰蓝，「云影」才是干净的灰 |
| 光带端头露在画面里 | 一条柔光带被切了个圆钝的截口，看着像渲染 bug | 贴图是**有端头的椭圆**，宽度不够时端头就落在屏幕内 | 宽度盖满整屏还有富余，横向摆动收到比「多出来的那截」更小 |
| 背景贴图缓存吃掉 21 MB | 十几张柔光带贴图，内存占用偏高 | `transform.rotate` 按**外接矩形**收费：13° 就把 1360×110 撑成 1340×480 | 改逐列错位倾斜，同样观感只要 8.1 MB |
| 加关卡后 T06 用例失败 | 报「本关没有找到被挡住的箭头」 | 教学关插到第 1 关，它只有 3 支，消一支后全场畅通 | 改成按关卡名查下标，并把「这一关要有被挡的箭头」写成断言 |
| 「清空进度」点了两次还在确认态 | 按钮文字停在「确认清空？」 | 确认分支里忘了把 `reset_armed` 复位 | 清空后先复位再重建按钮 |
| 教学高亮把箭头压暗 | 目标箭头看着像蒙了一层灰 | 高亮环的半透明填充画在箭头之后 | 底色改画在箭头下方，只有外环画在最上层 |
| 存档用 `pickle` 有崩启动的风险 | 文件损坏时 `pickle.load` 直接抛异常 | 方案没有考虑异常路径 | 换 JSON + 读写容错（读失败当空进度，写失败只警告） |
| 测试名字和作业编号对不上 | 名叫 `test_t04_*` 的用例测的却是「点到空格子」 | 规则层先占用了 T04~T06 这三个编号 | 规则层改名；把「清空通关 / 生命值耗尽 / 重新开始」三条整机用例命名为 T04~T06 |

## 八、PSP 表格

记录的是从零到可提交的整个开发周期（含需求拆解、编码、测试、文档与截图）。

| 任务 | 预估耗时（小时） | 实际耗时（小时） | 差异（小时） |
| --- | --- | --- | --- |
| 需求分析与游戏设计 | 1.5 | 1.0 | -0.5 |
| Python 与图形库学习 | 1.0 | 0.5 | -0.5 |
| 游戏界面实现 | 3.0 | 7.5 | +4.5 |
| 路径与碰撞逻辑实现 | 2.0 | 2.0 | 0.0 |
| 关卡设计 | 2.0 | 5.0 | +3.0 |
| AIGC 辅助开发 | 2.0 | 3.0 | +1.0 |
| 测试与修改 | 2.5 | 4.5 | +2.0 |
| README 与博客撰写 | 2.5 | 3.5 | +1.0 |
| **合计** | **16.5** | **27.0** | **+10.5** |

**差异分析**：

* **游戏界面超支最多**（+4.5）：界面本身不难，难在**反复看了不满意**——
  配色、动态背景、像素心、扣血动画，做完之后又回头重做；
  中间还照着参考图整体重做了一版（纯色点阵、糖果色箭头、居中信息栏、工具栏），
  最后又把**棋子模型从「一格一支箭头」换成「占多格的弯曲箭头」**——
  这一次改动牵动了渲染、规则、关卡数据、工具链和全部测试；
  提交前又把**飞出动画从整条平移改成沿路径滑出**（见第四节记录 14）。
  视觉上的「差不多」和「看着舒服」之间差距很大，而「换个表示法」的代价比预想的大得多。
* **关卡设计严重超支**（+2.5）：原本以为摆几关文本布局就完事了，结果
  ①手摆的布局出现无解，②生成的布局全是简单关，③提高密度反而更简单，
  ④同色扎堆；改成箭头模型之后**九个关卡又全部重做了一遍**。
  这一项也是收获最大的。
* **测试与修改超支**（+2.0）：预估时只想着作业要求的 T01–T06，
  实际每加一个功能（解锁、教学关、生命值、得分、计时、提示、辅助线、缩放、双主题）
  都要补回归用例；两次整体重做又让一批测试直接失效，只能跟着 API 一起重写。
  最后涨到 240 个。不过这些用例也确实抓到了真问题（清空进度没有复位、
  教学关插到第 1 关导致 T06 失效、辅助线几何算错）。
* **路径与碰撞逻辑持平**（0.0）：这是最核心的算法，但把四个方向统一成
  `(行增量, 列增量)` 之后，循环只有两份，边界问题从根上避免了。
  「先把数据结构想清楚再写代码」在这里省下了大量时间——
  也正因为规则层干净，改箭头模型时才能确定「只改表示、不改正确性」。
* **文档撰写略超**（+1.0）：博客不只是记录，还要挑出「AI 给了什么、我改了什么」的真实细节；
  而且每次重做都要把 README、博客、测试报告、检查清单四份文档一起同步，
  这部分比写使用说明费时间，但这些细节恰好是最有价值的部分。

## 九、心得体会

1. **AI 写代码很快，但「验收」只能靠自己。** 这次真正花时间的不是写代码，
   而是把每个环节真的跑一遍：一跑就发现字体崩溃、一跑就发现第 2 关无解、
   一跑就发现 GIF 有 8 MB。代码看起来再对，不运行就不算数。

2. **能自动校验的东西一定要自动校验。** 「关卡必须可解」这件事，用眼睛看 4 个布局也许能看出来，
   但关卡一旦扩到 9 个就必然出错。写成求解器 + 单元测试之后，改布局完全不慌。

3. **让 AI 给出「可测试的结构」，比让它一次写对更重要。** 把规则模块和 pygame 彻底隔开之后，
   规则测试从「要开窗口、要模拟鼠标」变成「三行代码断言一个状态」，效率差了一个数量级。
   更关键的是：**后来把棋子模型整个换掉时，正是这层隔离让我能确定「改的只是表示法，
   规则的正确性没动」**——如果规则和渲染搅在一起，那次重做根本不敢做。

4. **测试失败不一定是源码的问题。** 首轮 4 个失败全是测试自己写错了，
   但排查过程必须回到源码去看 `grid` 和 `arrows` 的区别——
   这也是为什么「必须理解自己提交的代码」。

5. **「难」这件事得由人来定义，而且要用数据验证。** 让 AI 生成关卡时，它给的关卡逻辑上都成立、
   都能通关，但没有一关是「难」的——因为它没玩过游戏，不知道什么叫难。
   我先想清楚「这个游戏唯一会输的方式是点错一支被挡住的箭头」，
   才能把「难」翻译成「开局可点数要少」这条能写进代码的指标。
   更反直觉的是「塞得越多越难」——这一条**想当然是错的**，只有真的跑数据才会发现。

6. **「换个表示法」从来不只是换个数据结构。** 把「一格一支箭头」改成「占多格的弯曲箭头」，
   听起来只是渲染上的事；实际上规则代码、九个关卡、六个工具脚本、两百多个测试全部要跟着改。
   AI 会很听话地把你说的那部分改好，但**它不会告诉你连锁影响有多大**。
   判断影响范围、决定哪些要重写、哪些能复用，是人的活儿。

7. **AI 的方案经常「功能可用」就停了，异常路径是空白。** `pickle` 存档那件事就是典型：
   正常运行完全没问题，但存档一损坏游戏就起不来。凡是会落盘、会联网、会读外部数据的地方，
   都要自己追问一句「出错会怎么样」。

8. **测试全绿不等于做完了。** 有好几次用例全过，但截图一看就发现
   提示气泡跟着进了关卡、教学高亮把箭头压暗了、**辅助线斜穿整个棋盘**。
   逻辑正确和看起来正确是两件事，所以我把「自动生成截图和 GIF」也做成了项目的一部分，
   每次改完都过一眼。这一版最典型的那个 bug（辅助线画歪）就是**看图看出来的**，
   测试当时是全绿的。

9. **过程记录本身就是产出。** 这次踩的坑（无解关卡、生成器排序写反、密度陷阱、
   配色来回改、箭头重做、GIF 体积）比最终代码更有价值——它们说明「AI 辅助开发」
   不是把需求丢给 AI 就完事，而是要人一直站在中间判断、验证、纠偏。
   这也让我意识到自己最缺的其实不是写代码的能力，
   而是**把模糊的直觉翻译成可验证指标**的能力。

## 十、如何运行

```bash
git clone https://github.com/zsx123456/one-arrow-after-another.git
cd one-arrow-after-another
pip install -r requirements.txt
python main.py
```

第一次运行会直接落在开始界面。点「教学关」可以先熟悉规则，点「开始游戏」直接进第 1 关。
此后每次启动都会读取项目根目录的 `progress.json`，接着上次的进度继续
（这个文件已经加进 `.gitignore`，属于本机状态，不会上传）。
想从头再来就在「设置」面板里点两次「清空进度」。

详细的环境说明、操作方式和常见问题见仓库的 `README.md`；
完整的测试日志、关卡校验输出和每一关的参考通关顺序见 `docs/test-report.md`。
