## 二、项目介绍

### 2.1 游戏规则

棋盘上散布着朝向「上 / 下 / 左 / 右」四种方向的箭头。玩家点击某个箭头：

* 它前进方向上**没有其它箭头阻挡**：箭头沿自己的方向飞出棋盘并被消除；
* 前进方向上**有箭头挡路**：箭头不会消失，前冲一下再弹回、抖动、泛红，**丢掉一颗心**；
* 清空本关全部箭头即通关，剩下的心越多，本关得分越高；
* 心用光则本关失败，可以重新开始。

### 2.2 界面设计

一共五个画面：**开始界面**、**关卡总览**、**游戏界面**、**结果面板**（通关 / 失败 / 全部通关 /
教学结束，都是叠在游戏界面上的半透明面板）、**教学引导**（游戏界面的一种模式）。

游戏界面自上而下分成四块：**顶部信息栏 / 关卡提示条 / 棋盘 / 底部工具栏**。

* 信息栏上一行是关卡序号与关卡名，下一行把**计时、生命值、剩余箭头、本关得分**四组信息
  横排并**整体居中**。心数会随关卡变化（4~7 颗）、得分位数也会变，早期用一串写死的 x 坐标，
  每加一点内容都要人工核算会不会压住；现在先量出真实字宽再居中，内容怎么变都不会撞上。
* 棋盘**不画每一格的底框**，只有一片极淡的点阵。这个玩法的难度来自「在一堆箭头里
  找出能点的那支」，几十个空方框会让视线一直被拽住——那是「乱」不是「难」。
* 底部工具栏：左边圆钮「提示」、中间「重新开始」、右边圆钮「辅助线」，
  圆钮下面各标一行名字，开关打开时圆钮和字一起变蓝。

配色上，四个方向的箭头各用一个糖果色（**上=青绿　下=橙　左=紫　右=粉**），
并把四个颜色的感知亮度（`0.299R + 0.587G + 0.114B`）都锁在 179~181 之间——
这样整屏箭头看着才是「一套」的，不会有的刺眼有的发闷。
这条约定是用数值卡住的：测试里有一条断言盯着「四个颜色的亮度极差 < 5」。

### 2.3 主要功能与特色

**作业要求的基础功能**（全部实现）：图形界面、四方向箭头、鼠标点击选择、
前进方向阻挡判断、无阻挡飞出消失、有阻挡碰撞反馈、失误次数显示（本作做成生命值）、
3 个以上可通关关卡（做了 9 个 + 1 个教学关）、通关进入下一关、失败判定、重新开始。

**额外做的部分**：

| 功能 | 说明 |
| --- | --- |
| 教学关 | 独立入口，4 步逐步引导，引导能自愈（玩家乱点也不会卡住） |
| 关卡总览 | 3×3 卡片一览全部关卡状态，未解锁的显示挂锁并压暗 |
| 逐关解锁 | 通关才解锁下一关，跳关不算数 |
| 进度存档 | JSON 存档，记录已通关关卡与每关最高分，损坏也不影响启动 |
| 生命值制 | 生命值上限**按难度星级给**（4~7 颗心），越难容错越高 |
| 得分与星级 | 难度星级 1~5 星；得分按剩余生命值比例折算，零失误有 20% 完美奖励 |
| 悬停显示路径 | 绿色 = 畅通、红色 = 被挡，并框出挡路的箭头，调试副产品，对玩家很友好 |
| 关卡生成器 | 逆向构造 + 阻挡偏好，批量产出**必然可解**的关卡 |
| 自动校验 | 贪心求解器 + 单元测试，任何一关变成死局都会立刻报错 |
| 动态背景 | 两团缓慢漂移的光晕 + 四角轻暗角，全部预渲染缓存，不影响帧率；点阵纯色主题下星点与流星默认关闭（配置项可随时打开） |
| 计时 | 顶部信息栏显示本关用时，重新开始归零、本关结束后停表 |
| 提示 | 一键找出一支「能解锁最多其它箭头」的选择，亮起会自己淡出的青色高亮环 |
| 辅助线 | 开启后给每支箭头画一条淡色方向射线，扫视大片棋盘时更省力 |

## 三、实现思路

### 3.1 技术选型与模块划分

选 Pygame 的理由很直接：动画和逐帧控制是它的主场；用 Surface 缓存 + `transform.rotate`
可以「画一次朝右的箭头，再旋转出四个方向」；而且它**无头运行方便**——
把 `SDL_VIDEODRIVER` 设成 `dummy` 就能不开窗口批量出截图、跑测试。

我先让 AI 帮我拆了一遍模块，得到的是「一个几百行的 main.py 里什么都有」。
这个方案能跑，但没法测——规则逻辑和 `pygame.display` 搅在一起，写测试就得先开窗口。
所以我要求按下面这种方式重做，核心原则是**规则模块不许 import pygame**：

```
game/
├── config.py    全局配置：窗口尺寸、配色、字体路径、动画参数
├── board.py     棋盘规则：路径检测 / 飞出 / 生命值 / 胜负判定（纯 Python）
├── levels.py    关卡数据：ASCII 布局 + 教学步骤 + 难度与生命值表
├── scoring.py   得分规则（纯函数）
├── progress.py  解锁规则与存档（纯 Python）
├── ui.py        绘图工具：字体、文字、按钮、箭头、像素心
├── anim.py      动画：飞出、撞击抖动、飘字、心碎
├── bgfx.py      动态背景
└── app.py       游戏主体：场景状态机、事件分发、渲染
```

收益非常明显：`board.py` / `progress.py` / `scoring.py` 都可以用纯逻辑测试覆盖，
跑一次不到 0.1 秒；关卡是否有解能脱离游戏单独验证；界面改版不会碰到规则代码。

### 3.2 箭头、方向和关卡怎么表示

**方向**用两个东西表示：一个字符 + 一个增量对。字符用于读写关卡，增量对用于算法。

```python
ARROW_CHARS = {">": RIGHT, "^": UP, "<": LEFT, "v": DOWN}
DELTAS = {RIGHT: (0, 1), UP: (-1, 0), LEFT: (0, -1), DOWN: (1, 0)}
```

把四个方向统一成 `(行增量, 列增量)` 是这一版最关键的设计决定，理由在 3.3 说。

**关卡**就是一段 ASCII 文本，`.>v<^` 一眼看懂，改关卡不用碰代码：

```python
Level(
    name="交叉路口",
    hint="全场只有一支箭能直接飞出去，先找到它",
    max_hp=4,
    layout=(
        ".....",
        ".>.v.",
        ".....",
        ".^..<",
        ".....",
    ),
)
```

`Level` 在 `__post_init__` 里就做校验：每行长度必须一致、只能出现合法字符、至少要有一支箭头，
教学关必须带引导步骤——**非法数据在构造时就报错**，不会等到画到屏幕上才发现。

### 3.3 路径检测（核心算法）

这是整个游戏的算法核心，两段代码就够了：

```python
def path_cells(self, row, col):
    """该箭头前进方向上、直到棋盘边界的全部格子坐标（不含自身）。"""
    arrow = self.grid[row][col]
    d_row, d_col = arrow.delta          # 方向 -> (行增量, 列增量)
    cells = []
    r, c = row + d_row, col + d_col
    while self.in_bounds(r, c):
        cells.append((r, c))
        r += d_row
        c += d_col
    return cells

def find_blocker(self, row, col):
    """返回前进方向上第一个挡路的箭头；路径通畅返回 None。"""
    for r, c in self.path_cells(row, col):
        if self.grid[r][c] is not None:
            return self.grid[r][c]
    return None
```

因为四个方向都被统一成增量对，所以**不需要写四份判断分支**：
朝上就是 `(-1, 0)`，朝右就是 `(0, 1)`，`while` 循环天然只沿一个方向推进，
边界由 `in_bounds()` 兜住，从根上避免了「向上判断时数组越界」这类经典错误。

### 3.4 单一状态入口：逻辑和表现彻底分开

所有对棋盘的修改都必须经过 `Board.click(row, col)`，它返回一个 `ClickResult`
（`fly` / `blocked` / `empty` / `ignored`）。界面层拿到返回值后只做一件事：决定播哪个动画。

```python
blocker = self.find_blocker(row, col)
if blocker is None:                        # 前方无阻挡 -> 飞出
    self.grid[row][col] = None
    self.remaining -= 1
    if self.remaining == 0:
        self.state = STATE_CLEARED
    return ClickResult(CLICK_FLY, arrow, None, path)

self.hp -= 1                               # 前方有阻挡 -> 丢一颗心
if self.hp <= 0:
    self.state = STATE_FAILED
return ClickResult(CLICK_BLOCKED, arrow, blocker, path)
```

这样测试可以完全绕过渲染直接验证规则，动画也永远不会反过来改状态。

### 3.5 飞出与撞击的表现

* **飞出**：`FlyOut` 动画用 `progress ** 1.7` 做缓入，看起来像被抽出去一样越来越快；
  飞出距离按「箭头位置 → 棋盘边界 + 0.9 个格子」计算，保证彻底离场；最后 28% 的时间里淡出。
* **撞击**：`Impact` 动画做三件事——沿方向前冲 18% 格宽再弹回（`sin` 曲线）、
  垂直于前进方向做衰减抖动、单元格泛红并向外扩散一圈红框，同时箭头颜色向红色插值。
  整个动画 0.36 秒，结束后自动从动画列表移除。
* **丢心**：`FloatingHeart` 把像素心复制成左右两半，每帧分开旋转、边倾斜边淡出往上飘，
  前 30% 时间保持不透明，避免玩家还没看清就消失。

### 3.6 生命值、得分与关卡难度

这一块是后期迭代出来的，我觉得是这次最有意思的部分。

**先定义「难」**。这个玩法有个容易被忽略的性质：点掉一支能飞出去的箭头，
只会让其它箭头的路径更空，所以**任何一步正确操作都不会把自己玩死**——
它不存在「顺序错误」，唯一会输的方式是点了一支其实被挡住的箭头。
于是难度**只来自一件事：在棋盘上找出此刻哪些箭头的前方是空的**。

**难度分**因此定为：

```
难度分 = 箭头数 × 1.6 + 密度 × 30 − 开局可点数 × 2.0      → 再映射成 1~5 颗星
```

刻意**不含生命值**：生命值现在是由难度分推出来的（见下），要是再把生命值算进难度分，
就成了「难度高 → 给的心多 → 难度算下来变低 → 星级跳回去」的循环。

**生命值按难度给**，因为越到后面越容易手滑：

```python
HP_BY_STARS = {1: 4, 2: 4, 3: 5, 4: 6, 5: 7}      # 越难容错越高
```

**得分按剩余生命值的比例折算**，而不是「每错一次扣固定分」：

```
基础分   = 星级 × 250
本关得分 = 基础分 × 剩余生命值 ÷ 生命值上限
完美奖励 = 一颗心都没丢时，再额外 +20% 基础分
```

为什么按比例：生命值上限逐关变大，固定扣分会让后面的关卡因为心多而显得无所谓
（第 9 关丢 1 颗心还剩 6 颗，扣的却和第 1 关一样多）。按比例折算则始终是
「这一颗心占本关全部容错的多大一份」，越到后面越宽容，和玩家直觉一致。

### 3.7 教学关、关卡总览与进度存档

**教学关**的引导要能**自愈**：玩家完全可以不按提示点。所以每一步在展示前都会和棋盘状态
对一次账——目标格子已经飞走了、或者这一步的前提（比如「它被挡住了」）已经不成立，
就自动跳到下一步，绝不会出现「让你去点一支已经不在棋盘上的箭头」这种尴尬。
实现在 `Game.sync_tutorial()`。

教学关**不放进 `LEVELS`**，而是单独的 `TUTORIAL` 常量：它不计分、不占关卡编号、
不需要解锁，主菜单上有独立入口。这样编号就从第 1 关「初次拉弓」干净地开始，
玩家也不会把教学关误当成一道要拿分、要解锁的题。

**进度存档**用 JSON 而不是 `pickle`（原因见第四节记录 6）：

```json
{ "version": 2, "cleared": [0, 1, 2], "scores": { "0": 300, "1": 600 } }
```

解锁规则只认**从头连续通关的前缀**，实现就是在第一个没通关的关卡处 `break`——
跳着通关不算数，难度递进不会被绕开。存档升级到 version 2 加了 `scores` 字段，
读的时候用 `data.get("scores", {})`，老存档读进来就是「都没得分」，不会因为升级而丢进度。

## 四、AIGC 使用过程

整个开发过程有 12 次比较有代表性的 AIGC 协作，总体情况如下：

| 子任务 | 借助何种 AIGC 技术 | AI 实现或提供了什么 | 效果如何 | 人工修改 |
| --- | --- | --- | --- | --- |

### 记录 1：第 2 关摆出了死局

**我的要求**：设计 4 个难度递进的关卡，用 ASCII 布局表示，第 2 关要「有且只有一支箭能直接飞出去」，
用来教玩家「先找出口」。

**AI 提供**：直接给了 4 关布局。第 2 关长这样：

```
.....          (1,1) 的「>」被 (1,3) 的「v」挡住
.>.v.          (1,3) 的「v」被 (3,3) 的「<」挡住
.....          (3,3) 的「<」被 (3,1) 的「^」挡住
.^.<.          (3,1) 的「^」被 (1,1) 的「>」挡住
.....
```

**实际效果**：开局可点的箭头数量是 **0**。四支箭头首尾相接围成一个环，互相指责，
谁都飞不出去——这一关是**无解**的。

**我的处理**：其实我当时也没一眼看出来，是写完校验脚本后报的警：

```
第2关 交叉路口  5×5  箭头4  初始可点0  可解=False
```

顺着「谁挡住了谁」捋一遍就明白了。修改办法很简单：把 `(3,3)` 的 `<` 挪到 `(3,4)`，
它左边依然是 `(3,1)` 的 `^`（保持阻挡关系不变），但不再挡在 `(1,3)` 的 `v` 下方了。
再校验就变成「唯一的出口 + 四步连锁」，正是我想要的效果。

**这件事的价值**：它让我意识到**关卡不能靠眼睛验收**。后来我把「所有关卡必须可解」
直接写成了单元测试，布局一改就会被自动拦住。

### 记录 2：为什么用贪心判断关卡有解

**我的要求**：写一个脚本，能自动判断关卡能不能通关，并给出一个参考通关顺序。

**AI 提供**：反复扫描棋盘，把当前能飞出的箭头全部消掉，直到不能再消；还有剩余就说明无解。

**实际效果**：跑起来完全正确。但我不太放心——「每次都消所有能消的」这种贪心，
会不会因为选择顺序不合适而漏掉真正的解？

**我的处理**：我补了一个证明，并把它写进了代码注释：

> 消除一个箭头只会让其它箭头的路径**变得更空**，永远不会让某条路径变得更堵。
> 也就是说「某箭头此刻能飞」这个性质具有**单调性**：此刻能飞，之后任何时刻都还能飞。
> 既然不会因为选择而失去任何机会，那么反复「消掉当前所有能飞的」就是完备的——
> 能全消掉就一定有通关顺序，卡住了就说明真的无解。

另外我还专门构造了一个**必然死锁**的布局做反向验证，这个用例跑通之后我才确信校验脚本可信。

### 记录 3：`pygame.font.SysFont()` 在本机直接崩溃

**我的要求**：界面全中文，需要加载系统中文字体。

**AI 提供**：教科书式的写法 `font = pygame.font.SysFont("Microsoft YaHei", 32)`。

**实际效果**：在这台 Windows 机器上，这一行**直接抛异常**：

```
File "pygame\sysfont.py", line 82, in initsysfonts_win32
    if splitext(font)[1].lower() not in OpenType_extensions:
TypeError: expected str, bytes or os.PathLike object, not int
```

原因是 pygame 枚举注册表里的字体项时碰到了不是字符串的条目，属于 pygame 2.6.1
在特定 Windows 字体环境下的兼容问题——**这是只有真的跑起来才会暴露的错误**。

**我的处理**：不再依赖 `SysFont` / `match_font`，改成自己按路径找字体文件，
依次尝试 `msyh.ttc` / `simhei.ttf` / `Deng.ttf`（Linux 和 macOS 各给一条路径），
都没有就退化为默认字体并在控制台警告。这样跨平台都能用，找不到字体也不会崩。

### 记录 4：测试用例首轮 4 个失败

**我的要求**：按作业给的 T01–T06 写自动化测试。

**AI 提供**：23 个用例，逻辑看着都对。

**实际效果**：第一次运行 **4 个失败**，原因分成两类，都不是源码的问题，而是测试自己写错了：

第一类，**测试关卡的箭头数写错了**（`AssertionError: 2 != 3`、`3 != 4`）。
测试布局里其实只有 3 支箭头，但断言按 4 支写——AI 把先前另一个草图的数量记串了。

第二类，**测试辅助函数把「已经飞出去的箭头」当成了「被挡住的箭头」**：

```python
def blocked_arrow(self, board):
    for arrow in board.arrows:
        if not board.can_fly(arrow.row, arrow.col):
            return arrow        # BUG：箭头飞出去后 can_fly 也是 False
```

`board.arrows` 保存的是**关卡初始的全部箭头**（用于重开时复位），箭头飞出去之后
它依然在列表里，但已经不在 `grid` 上了，于是 `can_fly` 返回 False，辅助函数就会误判，
结果点击时命中空格、根本不扣生命值，测试自然失败。

**我的处理**：断言数值按实际布局修正；辅助函数加一句「必须还在棋盘上」的过滤。

> 顺带一提：这是**首版**测试的数量。后面加了关卡总览、逐关解锁、教学关、
> 生命值、得分、计时、提示、辅助线，以及一路走来的配色回归之后，
> 用例扩到了 **103 个**，最终结果见第六节。

**这件事的价值**：测试失败不等于源码有 bug，也可能是测试自己在说谎。
两次都不是改游戏，而是改测试——但**前提是你得先看懂源码到底怎么运行的**，
这也正好说明「AI 生成的代码必须自己理解」不是一句空话。

### 记录 5：让 AI 生成关卡，结果它挑出来的全是最简单的

**我的要求**：再加几关，难度要递增，而且每一关都必须能通关。
随机撒箭头很容易撒出无解布局，所以我要求 AI 写一个生成器，用已有的求解器当验收。

**AI 提供**：`tools/generate_levels.py`，思路是「随机撒箭头 → 用贪心求解器筛掉无解的 →
按难度分排序取前几名」。

**实际效果**：筛出来的关卡确实都能通关，但**全部是开局几乎每支箭头都能飞出去的松布局**。
10×10 摆 30 支箭头，开局可点 24 支——玩家随便点都能过，难度根本谈不上。
翻代码才发现，排序那行我把方向写反了：难度分里「开局可飞行数」是负权重，
我却按升序取前几名，等于专门挑最简单的。

**我的处理**：先停下来想清楚一件事——**这个游戏到底难在哪里**（就是 3.6 节那段推理）。
想通之后，生成器换成两条新做法：

* **逆向构造**：把「消除顺序」倒过来当「放置顺序」，放置时只要求「新箭头正前方没有已放置的箭头」，
  这样放置顺序的逆序天然就是一个合法通关顺序，布局**必然可解**，连事后筛选都不需要；
* **阻挡偏好**：维护一张 `seen` 表，记录每个格子「被多少支已放置箭头的射线覆盖」，
  放置新箭头时优先选这些格子——新箭头正好落在老箭头前方，老箭头就得等它先走。
  这张表让判断「这格会不会挡住别人」变成 O(1)，不然每放一支都要重扫全盘。

结果：同样是 10×10 / 30 支箭头，开局可点数从 24 支压到 **7 支**，玩起来才真的需要一行一行地扫。

**这件事的价值**：排序方向写反是个很低级的错误，但更值得注意的是——
**AI 不会觉得「挑出来的关太简单」有什么不对**，因为它没有「这一关玩起来应该是什么感觉」的直觉。
「什么叫做难」这件事必须由人先定义清楚，再翻译成能写进代码的指标。

### 记录 6：进度用 pickle 存，看着能用其实是个雷

**我的要求**：记录玩家已经通关到第几关，没通关前面就不让玩后面；关掉游戏再打开，进度还在。

**AI 提供**：把已通关关卡的下标集合 `pickle` 到一个文件里，启动时 `pickle.load` 读回来。

**实际效果**：能跑。但有两个问题一看就心里发毛：

1. `pickle` 是二进制，存档出问题时**打不开也看不懂**；
2. 只要文件损坏（比如写到一半断电），`pickle.load` 会直接抛异常，
   **整个游戏在启动时就崩掉**——对一个要交给老师演示的作业来说这是致命的。

**我的处理**：

* 换成 JSON：存档打开就是 `{"version": 2, "cleared": [0, 1, 2], "scores": {...}}`，一眼能看懂；
* 加容错：读失败当作空进度，写失败只在控制台警告一次，游戏照常能玩。
  这是一个有取舍的决定——严格报错更「正确」，但演示场景下「能继续玩」更重要；
* 把解锁规则从界面代码里抽出来，放到不依赖 pygame 的 `progress.py`，
  于是「通关一关才解锁下一关」这条规则可以用普通单测覆盖，不必为了测一条 `if` 去创建窗口。

**这件事的价值**：AI 给出的方案经常是「功能可用」就停了，**异常路径完全是空白**。
凡是会落盘的东西，都要自己问一句：文件损坏了会怎么样？目录没写权限会怎么样？

### 记录 7：「塞得越多越难」，实测正好相反

**我的要求**：后面几关再难一点。

**AI 提供**：很自然的建议——把棋盘放大到 10×10，再往里多塞箭头，密度上去难度就上去。

**实际效果**：放大棋盘确实有用，但**提高密度完全没用，甚至反着来**。
实测数据很反直觉：

| 棋盘 | 箭头数 | 密度 | 开局可点数 |
| --- | --- | --- | --- |
| 9×9 | 30 支 | 0.37 | 7 支 |
| 9×9 | 54 支 | 0.67 | **18 支** |

塞进去的箭头多了将近一倍，开局能直接点的反而从 7 支涨到 18 支，比稀疏时还简单。

**原因是我想了一会儿才想明白的**：**贴着棋盘边缘、朝着棋盘外的箭头，它的射线长度是 0，
永远能飞**。密度一高，剩下的合法放置位置几乎只剩这一类（它们永远合法），
于是整个布局退化成「一大半箭头开局就能点」的松局面。

**我的处理**：给生成器补两条：

1. **排除空射线候选**：除最后一步外，一律避开射线为空的候选位置；
2. **打分里加上「自己射线的长度」**：`seen × 1 + raylen × 3`。
   只优化「能挡住别人」（`seen`）而不优化「能被别人挡住」（`raylen`）是不够的。

改完之后同样是 9×9，塞 50 支箭头（密度 0.62）时开局可点数从 18 支压到 **5 支**，
密度这才真正变成一条可用的难度轴。现在第 8 关起棋盘**冻结在 9×9**，
之后的难度全部来自密度，这条约束也写成了断言钉在测试里，防止以后又退回「放大棋盘」的老路。

**这件事的价值**：AI 给的方案在**逻辑上**都没错——多放箭头确实会让棋盘更挤。
错的是它没有「玩起来是什么感觉」这一层判断，而这层判断只能靠自己跑一遍数据才能发现。
**能算的就要算，不要凭感觉。**

### 记录 8：同色箭头扎堆，「颜色糊成一片」

**我的要求**：关卡里的颜色有点单调，想让它看起来丰富一些。
后来我又补了一句更具体的：「不同颜色的箭头混在一起，而不是相同颜色的箭头扎堆，
**不用修改箭头颜色**」。

**AI 提供**：第一版方案是给每个方向配 4 档明暗变体，用坐标挑档
（`(row * 3 + col * 5) % 4`，3 和 5 都与 4 互质，保证相邻格必定不同档）。

**实际效果**：同向相邻占比确实降下来了，但**新的问题出现了**——同一方向内感知亮度跨度到了
71~79（浅到深差三倍），看起来不是「丰富」而是「杂乱」。于是我又得回头要求「统一」。

**我的处理**：分两步走，而且第一步是**先量化**：

* 写脚本统计「相邻且同向的箭头占比」和「同方向 4-邻接连通块的最大格子数」，
  发现第 7 关相邻同向对占 **59%**、最大同色块 6 格——确实是扎堆，不是我的错觉；
* 去掉明暗变体，**一个方向就一个颜色**，把四个颜色的**感知亮度拉平**到差 1.7 以内
  （用 `0.299R + 0.587G + 0.114B` 算，而不是 HSL 的 L）；
* 单独写了 `tools/deshuffle_levels.py`：**位置一格不动，只逐个试换方向**。
  每换一次必须同时过三道闸——同向相邻对减少、开局可点数不增加、换完仍然可解。

处理完 6 个关卡的同向相邻占比从 45%~67% 降到 **11%~22%**，同色块从 7 格降到 4 格，
而**开局可点数一支都没变**（难度没被顺手改掉）。第 6 关更是直接在生成器里按这条线筛出来的，
25% 正好是四个方向完全交错的理论值。

**这件事的价值**：用户说「不好看」时，别直接开始调色——先把这句话变成一个**可测量的数字**
（同向相邻占比、亮度跨度），改完再拿同一个数字验证，否则只是在凭感觉换配色。
另外也说明**用户两次看似矛盾的要求（先「太单调」后「要统一」）其实说的不是一回事**：
前者指同类元素连成一整块，后者指同类元素之间深浅不一，两边都要满足。

### 记录 9：加完新功能，回归挂了两个用例

**背景**：加上关卡总览、逐关解锁、教学关之后跑一遍回归，挂了 2 个用例。两个都挺有意思。

**还有两个只有看图才能发现的问题**

跑完测试全绿之后我照例重新生成截图，一张一张看，发现两处：

* **「先通关第 N 关吧」的提示气泡会跟着玩家进入关卡**——切换场景时没有清掉气泡计时器；
* **教学关的高亮环把箭头压暗了**——高亮环的呼吸填充画在箭头之后，
  半透明的琥珀色盖在箭头上，看着像蒙了一层灰。改成底色画在箭头下方、只有外环画在最上层。

这两个都不是逻辑错误，**测试也测不出来**——是靠生成截图后逐张检查发现的。

**这件事的价值**：自动化测试能守住「逻辑对不对」，守不住「看起来对不对」。
一个可运行 + 可测试 + **有截图可复查**的项目，验收时才算闭环。

### 记录 10：照着参考图重做界面，返工全卡在「话没说清」

**我的要求**：找了一张同类游戏的截图当参考，让 AI 把界面改成那个样子——
纯色深紫背景、棋盘只留点阵（不要卡片格子）、箭头做成**糖果色的胖管子**、
顶部居中一条信息栏（关卡名 / 倒计时 / 生命值 / 剩余箭头数 / 得分）、
底部一排工具按钮。顺带把按钮背后真正接上的功能补出来：
**提示、重新开始、辅助线**。

**AI 提供**：一次给全了配色常量、箭头绘制函数、图标集和整块 HUD 布局。
第一版跑起来大方向是对的，但截图逐张看下来，还是有三处不对味：

1. **棋盘还留着卡片格。** 参考图是纯色点阵，AI 却沿用了上一版的「星空背景 + 带边线的方格」。
   原因是我第一次描述时只说了「箭头要像管子」，没提棋盘本身要改——
   等我把话说到「每格只留一个半透明白点、不要边框」，它才一次改到位。
2. **四个方向的颜色亮度不齐。** 上、下、左、右分开看都挺好看，
   摆在一起就有一支明显偏亮，「胖管子」的质感反而散了。
3. **教学关的提示条被底部工具栏压掉了。** 新加了工具栏，却没有把这块高度从棋盘区域里预留出去。

**我的处理**：

- 棋盘重做成**点阵**：每格画一个约 26/255 透明度的白点；
  已经走过的路径只铺一层很淡的色块，并且**向内缩 7 像素**——
  否则一条路径连起来像几块污渍。
- 颜色不靠眼睛调，改成**算亮度**。用 `0.299R + 0.587G + 0.114B`
  把四个方向锁在 **179–181**（极差 < 5），并**写成断言**：
  以后谁再动配色，只要破坏这个范围，测试立刻变红。
- 布局不再手写坐标，改成**从常量推导**：信息栏高度、工具栏高度、教学提示条高度
  先进布局计算，再交给绘制层用；顺手补了一条「各分区矩形互不重叠」的用例。
- 另外修掉了标题里「教学关」重复出现两次的小毛病。

**这件事的价值**：做界面最费时间的不是写绘制代码，而是**把「我要什么」说清楚**。
我说「箭头要像管子」，AI 就只改了箭头，棋盘还是老样子；
我说「每格只留一个点、不要边框」，它一次就到位。
**一句模糊的需求，换来的是一整轮返工**——这是这一轮我最大的体会。

还有一点：**「看着差不多」的东西，最好换成能算的指标。**
把亮度写成断言之后，改配色就从「凭感觉」变成了「看数字」。

## 五、关卡设计与可解性

### 5.1 教学关（独立入口，不计分）

| 关卡 | 棋盘 | 箭头数 | 生命值 | 引导步骤 |
| --- | --- | --- | --- | --- |
| 教学关 | 4×5 | 3 | 6 | 4 步：先点一支被挡的（感受碰撞）→ 点能飞的 → 回头点第一支（挡路的走了）→ 清空通关 |

教学关的引导第一、二步是刻意安排的：**先让玩家点一支飞不出去的箭头**——

**满分合计 9300 分。**

难度曲线的做法是**先量、再插**。九个关卡的难度分是
`5.2 / 9.2 / 19.1 / 22.5 / 33.8 / 43.7 / 56.1 / 70.8 / 88.5`，
相邻差 `4.0 / 9.9 / 3.4 / 11.3 / 9.9 / 12.4 / 14.7 / 17.7`——越往后加得越多，
前面留足台阶让人上手，后面才开始认真。

中间有一版是 8 关，相邻差里出现过 **22.3 分**的大台阶（第 5→6 关，箭头数 18 → 30，1.67 倍）。
我没有把新关追加到末尾（那样最陡的台阶会原样留着，玩家会在那一关突然卡住），
而是**插在最陡的那一处**，把一跳拆成 9.9 + 12.4 两段。插完再复查三件事：
难度严格递增、生命值不下降、棋盘尺寸不倒退——这三条也写成了断言。

## 七、遇到的问题汇总

| 问题 | 现象 | 原因 | 解决方式 |
| --- | --- | --- | --- |
| 第 2 关无解 | 校验脚本报 `可解=False`，开局可点箭头为 0 | 4 支箭头首尾相接形成死环 | 把 `<` 从 (3,3) 移到 (3,4)，重新校验 |
| 中文字体加载崩溃 | `TypeError: ... not int` | pygame 枚举 Windows 注册表字体时崩溃 | 改为按路径直接加载 `msyh.ttc` 等字体文件 |
| 测试首轮 4 个失败 | 断言数值对不上 / 点击不扣生命值 | 测试关卡的箭头数写错；辅助函数把已飞出的箭头当成被挡的 | 按实际布局修正数值；辅助函数加「箭头仍在棋盘上」的过滤 |
| 悬停高亮高亮了不该高亮的格子 | 挡路箭头之后的路段也被点亮 | 高亮用了完整路径，没在阻挡处截断 | 把路径截断到挡路箭头为止 |
| 动画还没播完就弹出结果面板 | 最后一支箭头还在飞，通关面板已经盖上来 | 状态切换和动画没有解耦 | 通关 / 失败后延迟 0.70 秒再弹面板，动画时长 0.45 秒 |
| 生成的关卡全是简单关 | 10×10 摆 30 支箭头，开局可点 24 支 | 难度分排序方向写反，等于专挑最简单的 | 改成降序，并换成「逆向构造 + 阻挡偏好」，开局可点压到 7 支 |
| 提高密度反而更简单 | 9×9 塞 54 支箭头时开局可点 18 支（塞 30 支时只有 7 支） | 贴边、朝棋盘外的箭头射线为 0，永远能飞；密度一高就只剩这类位置可用 | 生成器排除空射线候选，并给「自己射线长度」加权 |
| 同色箭头扎堆 | 一整排同向箭头贴在一起，屏幕上是一片同色 | 布局只关心「谁挡谁」，没管方向的分布 | 写 `deshuffle_levels.py`：位置不动只换方向，同向相邻占比 59% → 21% |
| 配色忽明忽暗 | 同一方向的箭头深浅不一，看着杂乱 | 用固定 HSL 亮度取 4 档变体，但感知亮度差到三倍 | 去掉变体，一方向一颜色，用加权公式把四色亮度拉平到差 1.7 以内 |
| 加关卡后 T06 用例失败 | 报「本关没有找到被挡住的箭头」 | 教学关插到第 1 关，它只有 3 支箭头，消一支后全部畅通 | 改成按关卡名查下标，断言「这一关要有被挡的箭头」 |
| 「清空进度」点了两次还在确认态 | 按钮文字停在「确认清空？」 | 确认分支里忘了把 `reset_armed` 复位 | 清空后先复位再重建按钮 |
| 提示气泡跟着进了关卡 | 点锁着的卡片后进关卡，气泡还在屏幕上 | 切换场景时没有清掉气泡计时器 | 把气泡清理并入场景公共清理函数 |
| 教学高亮把箭头压暗 | 目标箭头看着像蒙了一层灰 | 高亮环的半透明填充画在箭头之后 | 底色改画在箭头下方，只有外环画在最上层 |
| 存档用 `pickle` 有崩启动的风险 | 文件损坏时 `pickle.load` 直接抛异常 | 方案没有考虑异常路径 | 换 JSON + 读写容错（读失败当空进度，写失败只警告） |
| 写死的关号过期了不报错 | 校验脚本打印「棋盘尺寸到第 7 关封顶」，实际已经是第 8 关 | 文档字符串和报告里的关号是手写的常量 | 改成从关卡表现算，并 grep 一遍所有「第 N 关」 |

**差异分析**：

* **路径与碰撞逻辑比预估快**（-0.5）：这是本次最核心的算法，但把四个方向统一成
  `(行增量, 列增量)` 之后，两份小函数就写完了，而且没有出现越界之类的边界问题。
  「先把数据结构想清楚再写代码」在这里省下了大量时间。
* **游戏界面超支最多**（+2.0）：界面本身不难，难在**反复看了不满意**——
  配色打散、箭头配色统一、动态背景、像素心图标、扣血动画，这些都是第一版做完之后
  又回头重做的；最后还照着参考图**整体重做了一版**（纯色点阵、糖果色胖箭头、
  居中信息栏、提示 / 辅助线工具栏），连布局都从写死坐标改成从常量推导。
  视觉上的「差不多」和「看着舒服」之间差距很大。
* **关卡设计严重超支**（+1.5）：原本以为摆几关 ASCII 就完事了，结果
  ①手摆的布局出现无解，②生成的布局全是简单关，③提高密度反而更简单，
  ④同色箭头扎堆——每一个都是要停下来重新定义「什么叫做难」才能解决的问题。
  这一项也是收获最大的。
* **测试与修改超支**（+0.5）：预估时只想着作业要求的 T01–T06，实际后面每加一个功能

* **文档撰写略超**（+0.5）：博客不只是记录，还要挑出「AI 给了什么、我改了什么」的真实细节，
  比单纯写使用说明费时间，但这些细节恰好是最有价值的部分。

## 九、心得体会

1. **AI 写代码很快，但「验收」只能靠自己。** 这次真正花时间的不是写代码，
   而是把每个环节真的跑一遍：一跑就发现字体崩溃、一跑就发现第 2 关无解。
   代码看起来再对，不运行就不算数。

2. **能自动校验的东西一定要自动校验。** 「关卡必须可解」这件事，用眼睛看 4 个布局也许能看出来，
   但关卡一旦扩到 9 个就必然出错。写成求解器 + 单元测试之后，改布局完全不慌。

3. **让 AI 给出「可测试的结构」，比让它一次写对更重要。** 把规则模块和 pygame 彻底隔开之后，
   规则测试从「要开窗口、要模拟鼠标」变成「三行代码断言一个状态」，效率差了一个数量级。
   后来加解锁、加得分也是同一招——抽出纯逻辑模块，一条 `if` 也能被单测覆盖。

4. **测试失败不一定是源码的问题。** 首轮 4 个失败全是我自己（或 AI）写的测试有问题，
   但排查过程必须回到源码去看 `grid` 和 `arrows` 的区别——这也是为什么「必须理解自己提交的代码」。

5. **「难」这件事得由人来定义，而且要用数据验证。** 让 AI 生成关卡时，它给的关卡逻辑上都成立、
   都能通关，但没有一关是「难」的——因为它没玩过游戏，不知道什么叫难。
   我先想清楚「这个游戏唯一会输的方式是点错一支被挡住的箭头」，
   才能把「难」翻译成「开局可飞行数要少、棋盘要密」这两个能写进代码的指标。
   更反直觉的是「塞得越多越难」——这一条**想当然是错的**，只有真的跑数据才会发现。

6. **AI 的方案经常「功能可用」就停了，异常路径是空白。** `pickle` 存档那件事就是典型：
   正常运行完全没问题，但存档一损坏游戏就起不来。凡是会落盘、会联网、会读外部数据的地方，
   都要自己追问一句「出错会怎么样」。

7. **测试全绿不等于做完了。** 有好几次用例全过，但截图一看就发现
   提示气泡跟着进了关卡、教学高亮把箭头压暗了、同一方向的箭头深浅不一。
   逻辑正确和看起来正确是两件事，所以我把「自动生成截图和 GIF」也做成了项目的一部分，
   每次改完都过一眼。

8. **过程记录本身就是产出。** 这次踩的坑（无解关卡、生成器排序写反、密度陷阱、
   配色来回改）比最终代码更有价值——它们说明「AI 辅助开发」不是把需求丢给 AI 就完事，
   而是要人一直站在中间判断、验证、纠偏。这也让我意识到自己最缺的其实不是写代码的能力，
   而是**把模糊的直觉翻译成可验证指标**的能力。

## 十、如何运行

```bash
git clone https://github.com/zsx123456/one-arrow-after-another.git
cd one-arrow-after-another
pip install -r requirements.txt
python main.py
```

第一次运行会直接落在开始界面。点「教学关」可以先熟悉规则，点「开始游戏」直接进第 1 关。
此后每次启动都会读取项目根目录的 `progress.json`，接着上次的进度继续
（这个文件已经加进 `.gitignore`，属于本机状态，不会上传）。
想从头再来就在「关卡总览」里点两次「清空进度」。

详细的环境说明、操作方式和常见问题见仓库的 `README.md`；
完整的测试日志、关卡校验输出和每一关的参考通关顺序见 `docs/test-report.md`。
